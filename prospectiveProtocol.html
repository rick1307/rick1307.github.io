LEAP Protocol Working Notes

Prospective Protocol

A working sketchpad for a possible future Protocol 2: more efficient use of block space, more expressive records, and room for capabilities we have not yet designed.

Nothing on this page is adopted protocol. This is the place to think, compare, discard, and refine ideas before anything becomes authoritative.

1. Current baseline

Protocol 1 is intentionally readable. Its strength is that a person can inspect a memo and understand the namespace and record type without a decoder.

Examples include records such as SFL-LEAP/BADGE/..., SFL-LEAP/EVENT/..., and SFL-LEAP/CHALLENGE/....

The tradeoff is byte efficiency. Human-readable words consume block space that could someday carry additional structured information.

2. What Protocol 2 would try to improve

  • Use the XRPL memo budget more efficiently.
  • Preserve backward compatibility with Protocol 1.
  • Allow more structured data without making the memo fragile.
  • Reserve room for future record types, flags, and state.
  • Keep decoding simple enough that the protocol can be documented and independently implemented.
  • Avoid spending capacity merely because it is available.

4. The bridge requirement

A future decoder should be able to read both generations:

Protocol 1 → readable SFL-LEAP format

Protocol 2 → compact structured format

Old ledger history stays valid. New records gain efficiency. The bridge is the decoder plus an unambiguous way to identify which protocol version produced the record.

5. Open design questions

Versioning: What is the smallest reliable marker that clearly distinguishes Protocol 2 from Protocol 1?
Record types: Which concepts deserve permanent numeric codes, and which should remain free-form?
Achievements: Should badge, event, and challenge remain distinct record types, or should Protocol 2 also expose an umbrella achievement concept?
Reserved capacity: How much of the code space should deliberately remain undefined?
Human inspection: How much readability should be preserved without a decoder?
Extensibility: What information would be valuable enough to justify moving away from the current readable format?

6. Design posture

The goal is not to make Protocol 2 complicated. The goal is to make it capable without wasting block space.

Every new field or code should have to earn its place. Unused protocol capacity is not empty; it is future optionality.
