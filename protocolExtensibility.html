Sailing Frog's Leap · LEAP Protocol Notes

Protocol Extensibility

The light-bulb moment: a one-kilobyte memo limit is not merely a restriction. It is a design problem about block space, meaning, and how efficiently a protocol can turn a small number of bytes into durable information.

1. Start with the scarce thing: block space

The XRP Ledger gives transactions a limited memo budget. The entire Memos field is limited to no more than 1 KB when serialized in binary form. The scarce resource is not “characters.” It is serialized ledger space.

Block space is durable state capacity. A protocol decides how much meaning we can place into that capacity without making the history unintelligible.
Block space
→
Memo budget
→
Meaning

The 1 KB memo limit is therefore a concrete example of the block-space thesis: every byte used in a memo becomes part of permanent shared ledger state.

2. The current protocol is human-readable

A readable protocol is easy to inspect and teach:

SFL-LEAP/BADGE/PANAMA-CREW
SFL-LEAP/CHALLENGE/LEAP-001
SFL-LEAP/EVENT/...

The advantage is obvious: humans can read it directly. The cost is also obvious: words consume bytes. If LEAP someday needs substantially more information, readability begins competing with block-space efficiency.

3. Encoding, compression, and compact binary are different

TechniqueWhat it doesMain idea
EncodingChanges representation.Hex or Base64 changes how bytes are represented; it does not by itself create more underlying room.
CompressionRemoves redundancy.Repeated or structured information can sometimes be represented with fewer bytes, then reconstructed later.
Compact binary protocolDefines meaning directly in bytes, bits, positions, and codes.Instead of storing the words, store a compact code whose meaning is already known by the protocol.

The important shift is this: we do not always have to store the sentence. We can store enough information for a decoder to reconstruct the meaning.

4. Why “compact binary protocol”?

CompactIt uses as few bytes as practical. Repeated words and labels can become small numeric codes.
BinaryThe ledger ultimately stores bytes. Those bytes can carry values directly instead of spelling everything out as text.
ProtocolThe writer and reader agree on the rules. The bytes have meaning because the protocol defines what they mean.

It does not have to be one enormous lookup list. A lookup table can be part of it, but a compact protocol can also use fixed positions, bit flags, numeric ranges, and version markers.

5. The lookup table is the dictionary

The simplest version can literally be a dictionary:

01 = BADGE
02 = EVENT
03 = CHALLENGE

10 = PANAMA-CREW
11 = LEAP-001
12 = LEAP-OG

A JavaScript decoder could read 01 10 and reconstruct BADGE / PANAMA-CREW.

But the protocol can become more compact than a lookup table alone. One byte contains eight bits. Different bits can be assigned different jobs. Position itself can carry meaning, much like a VIN: the decoder already knows what a particular position represents.

6. The bridge lets the protocol evolve

Protocol 1

Human-readable

SFL-LEAP/BADGE/PANAMA-CREW

Easy to inspect. Uses more bytes.

↔
Protocol 2

Compact binary

02 01 10 ...

More efficient. Requires a decoder.

Nothing says a future LEAP protocol must look like the current one. The decoder can understand multiple generations at once.

if record is Protocol 1:
    decode the readable SFL-LEAP format

if record is Protocol 2:
    decode the compact binary format

if record is Protocol 3:
    use the future rules we have not invented yet

That is the bridge. Old ledger entries do not need to be rewritten. They remain valid historical records. New records can use a more capable protocol, and the software can continue to understand both.

7. A version marker creates backward compatibility

A compact protocol should identify which decoding rules apply. The simplest design is a small version marker near the beginning:

01 = compact protocol version 1
02 = compact protocol version 2
03 = future protocol version 3

That tiny version value buys enormous extensibility. It allows the meaning of future bytes to evolve without corrupting the meaning of old bytes.

Versioning turns a fixed memo limit into an evolving language.

8. Protect unused capacity

The lesson is not “pack the memo as full as possible.” It is almost the opposite. Unused capacity is optionality.

  • Do not consume ledger space merely because it is available.
  • Use readable text while readability is worth more than compactness.
  • Move to a compact protocol only when a real information need justifies the complexity.
  • Reserve version space and unassigned codes so the protocol can grow.
  • Keep the decoder backward-compatible so old history remains intelligible.

The next useful innovation may be something we cannot see yet. Protecting memo capacity keeps room for it.

9. The deeper idea

The protocol is not the data itself. The protocol is the agreement that lets a small amount of data represent a much larger amount of meaning.

Ledger bytes
→
Protocol version
→
Decoder
→
Human meaning

That is why this becomes an extensibility problem rather than merely a storage problem. A small code can represent a large shared concept, and a new version can introduce new rules later while old records remain readable.

Block space, bro: the scarce resource is the space. The protocol is how we make that space useful.
