Sailing Frog's Leap — Current Build Plan

Close the LEAP Loop

This plan reflects the system that exists now. Join intake, canonical Check creation, seven-day Manager cleanup, Crew Record pending notices, the permanent logbook, and Discord gating are already in place. The next work is about removing friction from cashing and proving the complete Check life cycle on a phone.

✓

Current Foundation

What is already part of the working LEAP system.
  • Join intake: a prospective member enters a public XRP Ledger address directly on join.html; Basin delivers the request without requiring an Instagram DM.
  • Create Check: Manager builds canonical recognition Checks from Badge, Event, or Challenge history, uses positive whole-number LEAP amounts, suppresses ordinary duplicates, and creates the one canonical public memo.
  • No normal ledger expiration: new LEAP recognition Checks omit the XRPL Expiration field.
  • Seven-day Manager cleanup: an open no-expiration Check becomes Cleanup Due in the Manager Checkbook after seven days. The Check is still cashable until it is cashed or canceled.
  • Seven-day Crew Record notice: a pending no-expiration Check is shown to the member for seven days from the validated CheckCreate timestamp, then the notice is hidden. The underlying Check remains on-ledger.
  • Permanent recognition: a Check-based Badge, Event, or Challenge enters the personal logbook only after that exact Check has been successfully cashed.
  • Discord: current LEAP membership can unlock the Discord connection flow and rank-based access.
Current operating rule Seven days is a Manager/Crew Record operating window, not an XRPL expiration. Cashing or cancellation is what closes a normal LEAP Check.

Cash My LEAP

Remove the biggest remaining member-side friction point.

Crew Record can already find a member's outstanding official LEAP Checks and show the amount, recognition reason, and seven-day notice window. The next step is to let the member start cashing the exact Check directly from that card instead of hunting through Xaman's Events screens.

Crew Record pending Check → Cash My LEAP → exact CheckCash handoff → Xaman review/sign → validated ledger → Crew Record updates
Safety boundary The website never receives a private key or signs for the member. It identifies the exact Check and hands the correct transaction to Xaman; the member reviews and signs there.
Done when A member with a pending LEAP Check can tap one obvious button on an iPhone, complete the cash in Xaman, return to Crew Record, and see the pending Check disappear and the resulting LEAP/history appear from validated XRPL data.
2

Prove the Three Xaman Handoffs

Create, Cash, and Cancel should all work predictably on the phone.

The Manager now builds unsigned transaction templates and can hand them to Xaman's Signing Tool. Before adding more system complexity, the complete life cycle should be tested until the behavior is boring and repeatable.

Create Check Manager builds the canonical no-expiration CheckCreate; Xaman signs; the validated Check appears in the Checkbook and recipient Crew Record.
Cash Check Crew Record identifies the exact outstanding Check; Xaman signs the matching CheckCash; the member's balance and logbook update.
Cancel Check Checkbook identifies a stale or unwanted Check; Xaman signs the exact CheckCancel; the object disappears and owner reserve is released.
Ledger confirmation Success is determined from validated XRPL state, not from whether a wallet screen merely looked successful.
Why this matters These three actions are the operating core of LEAP. Once they work cleanly, the system can grow without requiring members or the manager to understand XRPL mechanics.
Done when Create, Cash, and Cancel each produce the intended validated ledger result from the iPhone flow, and the Manager/Crew Record interfaces recognize the result correctly afterward.
3

Crew Profile / QR Identity

Keep the social layer as the next larger expansion after the operating loop is smooth.

The mental model remains the military ribbon rack: a fast visual read of where someone has been, what they have done, and how they fit into the crew.

A Leaper should eventually be able to show a QR code, let another person scan it, and open a live profile built from the member's public XRP Ledger address and validated LEAP history.

Share My Crew Profile Show a QR code that opens my public LEAP profile.
Get Crew Profile Scan another Leaper and open their live XRPL-backed profile.
Share QR → scan → public XRP Ledger address → live Crew Profile → rank + Badges + Events + Challenges
Intentionally deferred Final page name, nickname/call-sign rules, visual ribbon language, privacy/display choices, and exact QR URL format remain open. Do not let these decisions distract from finishing the Check life cycle first.
+

Measurement After the Cash Flow Works

Measure whether LEAP creates repeat participation rather than only first-time curiosity.
Visit → request first LEAP → Check issued → Check cashed → earns a second recognition

The most useful early business signal is not simply how many people request LEAP. It is how many successfully cash it and later return to earn another Badge, Event, or Challenge. That is the point where LEAP begins to demonstrate retention rather than novelty.

Do not overbuild this yet First make the member journey work. Then add only enough measurement to see where people fall out of the funnel and whether they come back.

The Current Build Order

  1. Cash My LEAP: make a pending Check easy for a member to cash from Crew Record.
  2. Validate the complete Check life cycle: Create, Cash, and Cancel from the iPhone/Xaman flow and confirm each result on-ledger.
  3. Add lightweight funnel measurement: request → issued → cashed → second recognition.
  4. Then return to Crew Profile / QR identity: expose the permanent record as a social identity once the core operating loop is dependable.

The guiding rule is simple: reduce friction before adding surface area. The machine should be easy to join, easy to operate, and easy to understand before it becomes bigger.
