LEAP Protocol

A working standard for how LEAP is identified, distributed, named, queried, interpreted, and used to establish membership, rank, events, challenges, badges, and permanent recognition on the XRP Ledger.

1. Purpose

The LEAP Protocol exists so that every future page, script, distribution, badge rule, and XRPL query interprets LEAP in the same way.

LEAP Standard
This document is the operating source of truth for LEAP. Public-facing pages may simplify these rules, but they should not silently invent different ones.

This protocol deliberately separates current state from historical fact. Current state answers questions such as “How much LEAP does this wallet hold now?” Historical fact answers questions such as “Was this wallet officially awarded Panama Crew?”

2. Core Principles

Current State Membership, balance, current rank, outstanding objects.
Historical State Awards, events, distributions, provenance, dates, transaction hashes.
Authority Only approved issuer/distributor activity can create official LEAP recognition.

Operating rules

  • Use validated XRPL data for decisions that affect membership, rank, or recognition.
  • Never treat a memo by itself as proof of official LEAP recognition.
  • Always verify LEAP currency identity and issuer identity together.
  • Never use a display label as the canonical machine identifier.
  • Once a canonical identifier has been used on-ledger, do not rename or reuse it.
  • Rank is dynamic. Historical recognition is permanent unless an explicit future revocation rule is created.
  • Each website page may query XRPL independently unless a future architecture change explicitly replaces that rule.

XRPL Fact
Standard XRPL currency codes are three characters. Nonstandard currency codes use a 160-bit hexadecimal value. Because LEAP is four letters, code must compare against the actual on-ledger currency value rather than assuming every API will return the literal text LEAP.

6. Namespace & Memo Standard

LEAP uses one short public memo string to identify the project, the recognition category, and the canonical value. The root namespace is SFL-LEAP.

LEAP Standard
The canonical public memo grammar is SFL-LEAP/<CATEGORY>=<VALUE>. One Check records one recognition reason, so one canonical recognition Check carries one public LEAP memo.

Current recognition categories

CategoryWhat it recordsCanonical example
BADGEPermanent recognition for something the member did, contributed to, attended, or was recognized forSFL-LEAP/BADGE=FIRST-MEMBER
EVENTA specific real-world or community occasion connected to the awardSFL-LEAP/EVENT=LA-CRUZ-BEACH-BONFIRE
CHALLENGEA numbered LEAP participation challengeSFL-LEAP/CHALLENGE=LEAP-001
Current Production Convention
One Check. One LEAP. One reason. One line in the logbook. Do not bundle a badge, event, and challenge into one Check. If a member earns two separate recognitions, create two separate Checks and give each Check its own canonical public memo.

Canonical grammar rules

  • The prefix is exactly SFL-LEAP/.
  • The category is one of BADGE, EVENT, or CHALLENGE.
  • Use one equals sign between category and value: =.
  • The value uses uppercase ASCII letters, numbers, and hyphens only.
  • Challenge values use the form LEAP-NNN, beginning with LEAP-001.
  • Do not add spaces around separators.
  • Do not append a date merely to preserve event timing; the validated XRPL ledger timestamp is authoritative.
  • The vertical bar character (|) is not part of the current recognition memo grammar and must not be used to bundle multiple recognitions into one Check.

Production examples

SFL-LEAP/BADGE=FIRST-MEMBER
SFL-LEAP/BADGE=LEAP-OG
SFL-LEAP/EVENT=LA-CRUZ-BEACH-BONFIRE
SFL-LEAP/CHALLENGE=LEAP-001
XRPL Fact
XRPL transactions can contain a Memos array. A memo can use the protocol fields MemoType, MemoFormat, and MemoData, which are represented as hexadecimal in transaction JSON. Wallet software may expose these fields through a simpler user interface.
Implementation Rule
The LEAP protocol standardizes the decoded public text, not a particular wallet's field layout. In Xaman's Check workflow, enter the complete canonical string into the single public memo box. Reader software should decode the transaction memo fields, normalize the wallet representation, and accept only a string that matches the LEAP grammar above.
Earlier draft structures may still be read for backward compatibility, but they are not used for new issuance. ORIGIN and PROTOCOL are not current member-recognition categories. Protocol versions belong to this operating document and its change log.

7. Transaction Standards

7.1 Official recognition distribution

Authorized Distributor
↓
CheckCreate
↓
Destination + 1 LEAP SendMax + one canonical public memo
↓
Member
↓
CheckCash
LEAP Standard
When a Check is used to deliver official recognition, the recognition memo belongs on the CheckCreate transaction because that transaction is created by the authorized LEAP distributor. The later CheckCash claims the Check; it does not replace the original recognition record.

7.2 Minimum checks for a canonical recognition CheckCreate

  • TransactionType = CheckCreate
  • Account is an authorized LEAP distributor
  • Destination is the intended member wallet
  • SendMax.currency is the canonical LEAP currency value
  • SendMax.issuer is the LEAP issuer
  • The current recognition workflow uses a value of 1 LEAP per Check
  • Transaction is successful
  • Transaction is in validated ledger history
  • Exactly one canonical SFL-LEAP/<CATEGORY>=<VALUE> public memo records the recognition reason

7.3 Check linkage

Store or derive the Check ledger object's ID from the successful CheckCreate metadata. A later CheckCash.CheckID can be matched back to that exact Check.

7.4 Direct Payment fallback

Direct LEAP Payments may be valid when deliberately used. When determining the amount actually delivered by a Payment, use transaction metadata rather than assuming the requested amount equals the delivered amount. The Check workflow remains the current onboarding and recognition standard.

8. Membership & Rank Rules

LEAP Standard
Membership and rank are determined from the wallet's current validated LEAP trust-line balance. They are current-state properties, not historical awards.
Current LEAP balanceMeaning
0No current LEAP membership status
1–4Deckhand
5–9Bosun
10–24Quartermaster
25–50First Mate

Rank can rise or fall as the wallet's LEAP balance changes. A badge or historical record does not disappear merely because the current balance changes.

9. Badge & Historical Recognition Rules

A badge represents something the wallet owner actually did, attended, contributed to, or was officially recognized for.

Badge validity test

VALIDATED
AND transaction result = success
AND originating account = authorized distributor
AND destination = member wallet
AND currency = canonical LEAP currency
AND issuer = canonical LEAP issuer
AND decoded public memo = SFL-LEAP/BADGE=registered badge ID
LEAP Standard
A matching memo created by an unauthorized wallet does not establish a badge. Provenance and content must both validate.

10. Event & Challenge Rules

Event

A specific real-world or community occasion connected to a LEAP distribution or recognition. Example: LA-CRUZ-BEACH-BONFIRE.

LEAP Standard
Do not add a year, month, or date to an EVENT identifier just to record when the event happened. Use the XRPL transaction's validated ledger timestamp as the event date for LEAP history. If the same named event happens again later, the EVENT value may remain the same; the validated transaction timestamp distinguishes the occurrence.

Challenge

A defined participation opportunity. Challenges receive unique sequential IDs and are never recycled. Example: LEAP-001. The next challenge receives the next unused number.

LEAP Standard
Event, challenge, badge, and rank are separate concepts. Do not overload one identifier to mean another.

11. Query Standards

11.1 Current membership / rank — account_lines

{
  "command": "account_lines",
  "account": "MEMBER_WALLET",
  "peer": "LEAP_ISSUER",
  "ledger_index": "validated"
}

Filter the returned line by the canonical LEAP currency value and issuer. Use the returned balance for rank.

11.2 Historical logbook — account_tx

{
  "command": "account_tx",
  "account": "MEMBER_WALLET",
  "ledger_index_min": "LEAP_GENESIS_LEDGER",
  "ledger_index_max": -1,
  "forward": true,
  "limit": 200
}

Follow marker pagination until the needed history is exhausted. Parse transactions and metadata; do not assume every transaction involving the account is a LEAP transaction.

11.3 Outstanding Checks — account_objects

{
  "command": "account_objects",
  "account": "MEMBER_WALLET",
  "ledger_index": "validated",
  "type": "check"
}

12. Transaction Validity Rules

Before website code treats an XRPL transaction as an official LEAP fact, validate all applicable conditions.

  • Data is from validated ledger history
  • Transaction result indicates success
  • Transaction type is allowed for the intended interpretation
  • Issuer matches the canonical LEAP issuer
  • Currency matches the canonical LEAP currency value
  • Authority account is authorized for the action
  • Destination or affected wallet matches the member being evaluated
  • Memo fields decode successfully when memo-based recognition is required
  • The decoded public memo normalizes to exactly one canonical SFL-LEAP/<CATEGORY>=<VALUE> record
  • The category is recognized and the value is a valid canonical identifier
LEAP Standard
Fail closed. If required provenance cannot be established, the website may display the transaction as history, but it must not convert it into official LEAP recognition.

14. Legacy / Pre-Protocol Transactions

Reader software may preserve compatibility with earlier LEAP memo experiments so genuine historical records remain readable. New issuance must use the canonical single-string format from Section 6.

Legacy patternInterpretationRule
MemoType=SFL-LEAP + MemoData=BADGE=...Earlier structured LEAP formRead-only compatibility after full authority, asset, destination, and validation checks
MemoType=SFL-LEAP/BADGE + MemoData=...Earlier split-memo proposalRead-only compatibility; do not create new records this way
Raw LEAP-OG or another free-form memoPotential pre-protocol markerDo not automatically grant recognition; map it manually only after provenance is verified
No LEAP recognition memoOrdinary earlier LEAP transfer/checkDo not infer badge, event, or challenge meaning without another authoritative rule
Backward-compatible readers are intentionally more tolerant than the production writer. The writer follows one current grammar; readers may understand older approved forms without making those forms current again.

15. Versioning & Change Control

VersionUse
0.xWorking drafts before the first production standard
1.0First approved production protocol
1.1, 1.2…Additive / backward-compatible rules
2.0Breaking interpretation change

Change rules

  • Never silently redefine an identifier already used on-ledger.
  • Never reuse a retired badge, event, or challenge ID for a different meaning.
  • Do not add a new recognition category without updating this protocol.
  • Record newly authorized distributors here before treating their transactions as official.
  • Keep old protocol versions readable so historical transactions remain interpretable.
  • Prefer additive changes over breaking changes.

16. Open Decisions / Next Work

These are intentionally unresolved. They should be settled before declaring Protocol 1.0.

  • Verify and record LEAP's exact 160-bit currency value from the live ledger.
  • Record the LEAP genesis / first relevant ledger index for efficient historical queries.
  • Inventory existing pre-protocol LEAP transactions and complete any legacy mapping rules that are actually needed.
  • Establish the first official event registry.
  • Maintain the challenge sequence so each new challenge receives the next unused LEAP-NNN identifier.
