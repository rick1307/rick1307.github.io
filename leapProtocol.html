Authoritative Current Protocol
Protocol 0.18 is the current authoritative LEAP Protocol for Wild Ledger. It defines the distinction between protocol-defined and community-defined recognition and defines GREAT-CHAT as the one recognition currently defined directly by the Protocol Core. It remains authoritative until changed by an explicit protocol revision under Section 15.

1. Purpose

The LEAP Protocol defines the durable rules that make LEAP activity interpretable across Wild Ledger communities and across time. It is written so that a future developer or AI can read this document, understand the protocol, and safely build against it without inventing new meaning.

LEAP Standard
Sections 1–6 are the authoritative source of truth for LEAP protocol meaning. Wild Ledger implements and presents that Protocol Core; it does not redefine it. Public pages, operator tools, wallets, signers, user interfaces, implementation notes, and later sections may simplify, explain, or improve the implementation, but they must not silently change the authoritative protocol rules.

LEAP deliberately separates current holdings from community-earned standing. “How much LEAP is in this wallet now?” and “How much LEAP has this member earned from this community?” are different questions and may have different answers.

Authority Boundary
Sections 1–6 define the authoritative Protocol Core. Sections 7–17 explain how to implement, query, validate, display, and evolve software around that core. Developers and AI may challenge or replace implementation approaches in Sections 7–17. They may not reinterpret Sections 1–6. If later guidance or code conflicts with the Protocol Core, the later guidance or code is wrong and must be corrected.

2. Core Principles

Recognition A member receives LEAP for an existing Badge, Event, or Challenge.
Lifecycle State No LEAP moves. The community publishes lifecycle state for community-defined recognition definitions.
Authority Protocol facts count only when the correct XRPL authority performs the correct protocol act.
Canonical State Principle
Canonical community state exists only on XRPL. Wild Ledger is an interpreter of canonical state, never its keeper. Protocol-defined constants, grammar, and meanings come from this Protocol Core. Every authoritative community-specific fact required to reconstruct what happened — including authority, lifecycle state, recognition awards, allocations, Earned LEAP, and rank inputs — MUST be recoverable from validated XRPL ledger history. Off-ledger storage, browser storage, configuration files, caches, or presentation logic MUST NOT constitute authoritative community protocol state.

Operating rules

  • Use validated XRPL data for canonical protocol facts.
  • Interpret protocol meaning from the transaction type, authorized provenance, canonical asset identity, canonical memo, and validated result together.
  • Never treat a memo by itself as proof of official LEAP activity.
  • Member recognition always involves LEAP moving to a member.
  • Recognition-definition lifecycle state never moves LEAP and never recognizes a member.
  • Recognition opportunities and member recognition history are separate views and must never be substituted for one another. Protocol-defined recognition comes from this Protocol Core; community-defined recognition state comes from validated XRPL lifecycle history; member-earned recognition comes from validated LEAP-bearing XRPL transactions.
  • Current LEAP balance is a current wallet fact. Earned LEAP is cumulative community history. They are not interchangeable.
  • Community rank is derived from that community's cumulative Earned LEAP, not from current wallet balance.
  • Moving LEAP after it has been earned does not erase the earning history or reduce rank.
  • Canonical machine identifiers remain stable even when friendly display labels change.
  • User-interface presentation is flexible. Protocol meaning is not.

3. Authority Registry

LEAP separates protocol-level asset identities, protocol-level Owner authority, and community-level Operating Wallet authority. The LEAP Issuer and LEAP Distributor are protocol-defined identities. Owner Wallet authority and Community Operating Wallet authority are resolved from validated XRPL authority-state history after their respective canonical establishment.

Role Separation
A Community Operator is the human or business role that runs a community. A Community Operating Wallet is the XRPL account authorized to perform that community's protocol transactions. The ledger authenticates the account that signed the transaction, not the human title behind it.
The Owner is an application and protocol-governance role. The Owner Wallet is the XRPL account that carries protocol provisioning authority. Being the human or application Owner does not, by itself, authorize an arbitrary XRPL account; protocol authority follows the canonical Owner Wallet history.
Owner Authority Rule
The current Owner Wallet may establish the first Community Operating Wallet for a Community ID that has never previously been established. After that establishment transaction validates, the Owner Wallet has no continuing authority to replace that community's Operating Wallet. The current Owner Wallet may transfer Owner authority by publishing a canonical OWNER-WALLET authority-state statement naming a successor account. From that ledger position forward, the successor is the current Owner Wallet.
Authority Resolution Rule
After a community has a canonical OPERATING-WALLET authority-state statement, the authorized Community Operating Wallet at any ledger position is the latest valid value for that community key immediately before the protocol act being evaluated. A matching memo from another account does not become official merely because the text is correct.
For a community that existed before on-ledger authority state, the already-established pre-authority-state Operating Wallet may publish the one-time initial canonical value naming itself. After that statement validates, future Operating Wallet replacement is performed by the currently authorized Operating Wallet through a new canonical authority-state statement.

Canonical ID Rule
Canonical IDs use uppercase ASCII letters, numbers, and hyphens only. Avoid spaces, underscores, punctuation, apostrophes, emojis, and decorative capitalization. Once a canonical ID is established on-ledger, its meaning must not be renamed, reassigned, or recycled.
Community ID Reservation
A Community ID is globally unique within Wild Ledger and is permanently reserved to that community once established. A different community must not reuse the ID and inherit another community's namespace history. The same continuing community may retain its existing ID across Operating Wallet changes or operator succession.

Recognition Definition Origins

Every recognition definition has one of two origins: protocol-defined or community-defined. The origin determines how the definition exists; it does not create a new recognition category. Badge, Event, and Challenge remain the recognition categories.

Two Definition Origins
A protocol-defined recognition exists because the LEAP Protocol Core defines it. It is available to every established LEAP community without a community lifecycle CREATE, and a Community Operator cannot CREATE, END, IGNORE, rename, or redefine it. A community-defined recognition exists only after a valid canonical lifecycle CREATE for that community and is thereafter governed by the community lifecycle rules.
Protocol-Defined Recognition
The LEAP Protocol currently defines one protocol-defined recognition: GREAT-CHAT. GREAT-CHAT is a Badge. It exists automatically for every established LEAP community and requires no community lifecycle transaction. Because GREAT-CHAT is a Badge, it follows the ordinary Badge recognition rules, including repeatability. Its protocol-defined status changes how the definition exists; it does not create a separate award mechanism or recognition category. Each award remains scoped to the awarding community through that community's namespace, for example SFL-LEAP/BADGE=GREAT-CHAT. A Great Chat award contributes only to that member's Earned LEAP and rank in the awarding community. The Protocol does not prescribe a Great Chat award amount; any award must satisfy the general LEAP recognition transaction rules.

Community-Defined Recognition IDs

A community-defined Badge, Event, or Challenge definition must be created before it can be awarded. Wild Ledger should validate or generate compliant canonical IDs so Operators do not have to manually construct protocol strings. Before creating a new community-defined definition, software must check the complete XRPL-derived history for that community and category and reject an ID that has already been established, ended, ignored, or reserved by the Protocol Core.

Broad-to-narrow specificity

Add qualifiers only when they distinguish the meaning of the recognition itself. Specificity proceeds from broad to narrow, left to right. The validated XRPL timestamp distinguishes transactions; a new date or suffix is not required merely because the same repeatable Badge is awarded again.

6. Namespace & Memo Standard

LEAP uses public memo strings across permitted XRPL transaction types. Community records use the root namespace <COMMUNITY>-LEAP. Protocol-level Owner authority uses the separate LEAP/AUTHORITY namespace. Each community has its own canonical namespace, while every community follows the same LEAP Protocol grammar and transaction semantics.

Interpretation Rule
Protocol meaning comes from the transaction type + authorized provenance + canonical memo + validated result together. The same text from the wrong account or on the wrong transaction type does not create the intended protocol fact.
Recognition vs. Lifecycle
Member recognition and recognition-definition lifecycle are separate by design. A member recognition transaction transfers LEAP to a member and records what that member earned. A lifecycle no-op AccountSet transfers no LEAP and records whether a community-defined Badge, Event, or Challenge definition exists and is available. Protocol-defined recognition does not use community lifecycle transactions. A lifecycle CREATE does not award recognition, and a member recognition transaction does not create or redefine a recognition definition.
Two Recognition Views
Wild Ledger constructs available recognition opportunities from protocol-defined recognition in this Protocol Core plus validated community lifecycle history, and reconstructs member-earned recognition from validated LEAP-bearing recognition transactions. Neither view substitutes for the other.

Recognition categories

CategoryMeaningExample award memo
BADGEReusable recognition for something a member did, contributed to, attended, or was recognized forSFL-LEAP/BADGE=GREAT-CHAT
EVENTA specific real-world or community occurrenceSFL-LEAP/EVENT=LA-CRUZ-BEACH-BONFIRE-2026
CHALLENGEA numbered participation opportunitySFL-LEAP/CHALLENGE=LEAP-001
One Recognition Rule
One recognition transaction. One recognition. One reason. One line in the logbook. A recognition transaction may deliver one or more whole LEAP, but it records exactly one Badge, Event, or Challenge reason.

Lifecycle actions

Lifecycle actions apply only to community-defined recognitions. Protocol-defined recognitions do not participate in the community lifecycle.

  • CREATE establishes the community-defined recognition and makes it available according to its category.
  • END normally ends future availability without erasing prior valid awards.
  • IGNORE terminally marks an erroneous, invalid, test, or otherwise non-operational definition. The ID remains permanently reserved.

XRPL Fact
LEAP is fungible. A memo is part of a transaction record; it does not travel with an individual LEAP unit. XRPL stores memo data but does not interpret the LEAP namespace. LEAP Protocol software performs that interpretation.
The protocol standardizes the decoded public memo text, not a particular wallet or signer's user interface.

7.0 Community allocation Checks

LEAP Distributor → CheckCreate → community delivery wallet → CheckCash
  • TransactionType = CheckCreate.
  • Account is the LEAP Distributor authorized at that ledger position.
  • SendMax identifies canonical LEAP and contains a positive whole-number amount.
  • Exactly one canonical <COMMUNITY>-LEAP/ALLOCATION=<AMOUNT> memo is present.
  • The memo amount matches the offered SendMax.value.
  • The transaction succeeds in validated ledger history.
Allocation Attribution Rule
A valid allocation belongs to the community named in the canonical allocation memo. The Check destination records where the allocation was delivered; it does not define community ownership. Later Operating Wallet changes do not orphan, transfer, or rewrite earlier community allocation history.

CheckCreate records the allocation offer. Successful CheckCash completes delivery. CheckCancel cancels an unredeemed delivery.

7.1 Member recognition by Check

Authorized Community Operating Wallet → CheckCreate → member → CheckCash → Earned LEAP
  • The recognition is protocol-defined and available under the Protocol Core, or its community-defined definition already exists and is available at the ledger position of the CheckCreate.
  • Account is the Community Operating Wallet authorized for that community at that ledger position.
  • Destination is the intended member wallet.
  • SendMax identifies canonical LEAP and contains a positive whole-number amount.
  • The standard recognition Check omits XRPL Expiration.
  • Exactly one canonical <COMMUNITY>-LEAP/<CATEGORY>=<CANONICAL-ID> recognition memo is present.
  • The CheckCreate is successful and validated.
Pending vs. Earned
A recognition CheckCreate is a pending recognition offer. It is not Earned LEAP until that exact Check is successfully cashed. The later CheckCash references the Check by CheckID. For official recognition, the cashing result must deliver a positive whole-number amount of LEAP. Earned LEAP is the amount actually delivered by the successful CheckCash, not merely the earlier SendMax offer.
XRPL Fact
A recipient does not need a pre-existing LEAP trust line before the recognition Check is created. Current XRPL behavior can create the required zero-limit trust line when an issued-token Check is successfully cashed.

7.2 Member recognition by Payment

Authorized Community Operating Wallet → Payment → member → Earned LEAP
  • The recognition is protocol-defined and available under the Protocol Core, or its community-defined definition already exists and is available at the ledger position of the Payment.
  • Account is the Community Operating Wallet authorized for that community at that ledger position.
  • Destination is the intended member wallet.
  • The Payment successfully delivers a positive whole-number amount of canonical LEAP.
  • Exactly one canonical <COMMUNITY>-LEAP/<CATEGORY>=<CANONICAL-ID> recognition memo is present.
  • The transaction succeeds in validated ledger history.
Immediate Recognition
A valid recognition Payment becomes Earned LEAP when the Payment validates successfully. Earned LEAP is based on the amount actually delivered. The receiving wallet must already be able to receive LEAP; how Wild Ledger represents that capability in the user interface is not part of the protocol.
XRP tips from members to a Community Operator are outside LEAP member recognition. They do not create Earned LEAP and do not affect community rank.

7.3 Recognition repetition

Category Semantics
A Badge definition may be awarded repeatedly to the same member. Each protocol-valid Badge recognition transaction is a separate award and its delivered LEAP contributes to Earned LEAP. Event and Challenge IDs identify specific occurrences or opportunities; for a given member, the same canonical Event or Challenge ID counts as one official earned recognition. A different occurrence or challenge receives its own canonical ID.
The protocol does not manufacture new Badge IDs merely to make repeated awards unique. Individual XRPL transactions already distinguish the awards.

7.4 Check state and cancellation

Standard recognition Checks have no protocol expiration. An open Check remains pending until it is cashed or canceled. A successful CheckCancel removes the outstanding Check ledger object but does not erase the historical CheckCreate transaction. A canceled, unredeemed recognition Check contributes no Earned LEAP.

Cleanup timing, reminders, buttons, wallet-specific navigation, and other operating conveniences are Wild Ledger policy and UI behavior, not LEAP Protocol state.

7.5 Community-defined recognition lifecycle — no-op AccountSet

Community-defined lifecycle state is separate from member recognition. It moves no LEAP, names no member, and tells Wild Ledger which community-defined recognition opportunities exist and whether they remain available. Protocol-defined recognition does not use this lifecycle.

Canonical Lifecycle Transaction
A lifecycle record is a successful, validated no-op AccountSet from the Community Operating Wallet authorized at that ledger position, containing exactly one canonical <COMMUNITY>-LEAP/RECOGNITION/<CATEGORY>/<CANONICAL-ID>/LIFECYCLE-TAG=<ACTION> memo and no AccountSet-specific mutation fields.
ActionProtocol meaning
CREATEBirth of the definition. Badge = Available; Event = Active; Challenge = Active.
ENDNormal terminal state. Badge = Retired; Event = Completed; Challenge = Closed. Prior valid earned recognition remains valid.
IGNOREExceptional terminal state for an erroneous, invalid, test, or non-operational definition. It is suppressed from normal recognition use and the ID remains permanently reserved.
Cradle-to-Grave Rule
CREATE begins the definition's lifecycle. END and IGNORE are terminal. There is no reopen, unend, or unignore action in the current protocol. Lifecycle changes do not erase the XRPL transaction history or reverse any token transfer that already occurred.
Permanent ID Reservation
Before creating a community-defined Badge, Event, or Challenge, Wild Ledger must reject a canonical ID already established in that community and category, including IDs later ended or ignored, and must reject an ID reserved by the Protocol Core such as GREAT-CHAT.
For a community that existed before canonical community authority state, the validated position of its one-time existing-community migration statement is that community's recognition lifecycle activation point. Definitions supported by valid authorized historical recognition records before that point remain readable as legacy-established definitions. Their IDs remain reserved and may later receive END or IGNORE without a retroactive CREATE. For a newly provisioned community, its first valid OPERATING-WALLET establishment transaction is both its canonical community-establishment point and its recognition lifecycle activation point. From that point forward, every community-defined recognition must be established by canonical CREATE before it can be awarded. Protocol-defined GREAT-CHAT is available automatically when the community is established and requires no lifecycle CREATE.

7.6 Community authority state — no-op AccountSet

Canonical Authority-State Transaction
A community authority-state record is a successful, validated no-op AccountSet containing exactly one canonical <COMMUNITY>-LEAP/AUTHORITY/<KEY>=<VALUE> memo and no AccountSet-specific mutation fields.

Existing-community migration

A documented pre-authority-state Community Operating Wallet may publish exactly one initial OPERATING-WALLET statement naming itself. After that statement validates, XRPL authority-state history is canonical for that community.

Brand-new community establishment

For a Community ID with no prior canonical community authority-state history, the current Owner Wallet may publish exactly one initial OPERATING-WALLET statement naming that community's first Community Operating Wallet. The sender must be the Owner Wallet authorized at that ledger position. When the transaction validates, the Community ID is permanently established and reserved, the named account becomes that community's authorized Community Operating Wallet, and XRPL authority-state history becomes canonical for that community from that ledger position forward. The Owner Wallet does not retain authority to replace the Operating Wallet of an established community.

Operating Wallet replacement

The currently authorized Community Operating Wallet may replace itself by publishing a valid OPERATING-WALLET statement naming the successor account. The sender must be the Operating Wallet resolved immediately before the transaction. The latest valid value wins from that ledger position forward.

Emergency recovery from a lost or compromised current Operating Wallet remains an explicit open protocol decision in Section 16.

7.7 Owner Wallet authority state — no-op AccountSet

Canonical Owner Authority-State Transaction
An Owner Wallet authority-state record is a successful, validated no-op AccountSet containing exactly one canonical LEAP/AUTHORITY/OWNER-WALLET=<ADDRESS> memo and no AccountSet-specific mutation fields.

Initial Owner Wallet establishment

The initial Owner Wallet designated in the Protocol Authority Registry may publish exactly one initial OWNER-WALLET statement naming itself. After that statement validates, XRPL Owner Wallet authority-state history is canonical.

Owner Wallet replacement

The currently authorized Owner Wallet may replace itself by publishing a valid OWNER-WALLET statement naming the successor account. The sender must be the Owner Wallet resolved immediately before the transaction. The latest valid value wins from that ledger position forward.

8. Membership & Rank Rules

Earned LEAP
Earned LEAP is the cumulative LEAP actually delivered to a member through protocol-valid recognition from a specific community. Check-based recognition contributes when the Check is successfully cashed. Payment-based recognition contributes when the Payment successfully validates.
Membership
For LEAP Protocol purposes, a wallet becomes a member of a community when it first earns LEAP from that community through valid recognition. Membership is historical community status and does not disappear merely because the wallet's current LEAP balance later falls to zero.

Rank Rule
Rank is derived from that community's cumulative Earned LEAP. Sending, spending, or otherwise moving LEAP after it was earned changes current holdings but does not erase the earned history or reduce rank. 9. Badge & Historical Recognition Rules

A Badge is a reusable recognition definition for something a member did, contributed to, attended, or was recognized for. The LEAP Protocol currently defines one Badge directly: GREAT-CHAT. Because it is a Badge, GREAT-CHAT follows the ordinary Badge rules, including repeatability. Other Badges are community-defined when established by valid community lifecycle history. Chat is not a separate recognition category.

Badge Lifecycle
For a community-defined Badge, a valid lifecycle CREATE makes it Available and a valid END makes it Retired for future awards. Retirement does not erase prior valid awards. A protocol-defined Badge is available according to the Protocol Core and does not use the community lifecycle.
Repeatable Badge Rule
A Badge may be awarded more than once to the same member. Each valid Badge recognition transaction is a separate award and the LEAP actually delivered by that transaction contributes to the member's Earned LEAP.

10. Event & Challenge Rules

Event

An Event is a specific real-world or community occurrence that members may be recognized for participating in.

Event Lifecycle
A valid CREATE makes an Event Active. A valid END makes it Completed. Completion ends future normal awards for that Event but preserves prior valid member history.

Many members may earn recognition for the same Event. For a given member, the same canonical Event ID represents one occurrence and counts as one official Event recognition. If a similar event occurs again, create a distinct canonical Event ID using only enough broad-to-narrow specificity to distinguish the new occurrence.

Challenge

A Challenge is a defined participation opportunity. Many members may complete the same Challenge while it is active.

Challenge Lifecycle
A valid CREATE makes a Challenge Active. A valid END makes it Closed. Closing ends future normal completion recognition but preserves prior valid member history.
Challenge ID Rule
Challenge IDs use the sequential form LEAP-NNN. Wild Ledger derives the next unused value from the complete XRPL-derived Challenge history. Challenge IDs are never recycled, including ended or ignored IDs.

For a given member, the same canonical Challenge ID counts as one official Challenge completion. Event, Challenge, Badge, and rank are separate concepts and must not overload one another's identifiers.

11. Query Standards

Query logic reconstructs protocol meaning from XRPL. Optimizations and caches are permitted, but they must not become canonical state.

11.1 Current LEAP — account_lines

{
  "command": "account_lines",
  "account": "MEMBER_WALLET",
  "peer": "LEAP_ISSUER",
  "ledger_index": "validated"
}

Filter by the canonical LEAP issuer and currency value. The resulting balance answers current holdings only; it does not determine Earned LEAP or rank.

11.2 Member Earned LEAP and recognition history — account_tx

Scan validated member history with pagination. For each candidate recognition, validate the community namespace, recognition origin and applicable definition state at that ledger position, authorized Community Operating Wallet, asset identity, destination, transaction type, result, and memo. For Check recognition, link the originating CheckCreate to the successful CheckCash by Check ID and use the amount actually delivered. For Payment recognition, use the amount actually delivered by the successful Payment.

11.3 Recognition opportunity catalog

Begin with protocol-defined recognition in this Protocol Core, which currently defines BADGE=GREAT-CHAT for every established LEAP community. Add community-defined Badge, Event, and Challenge availability from validated lifecycle AccountSet history produced by wallets that were authorized for the community at the relevant ledger positions. Process lifecycle records in canonical XRPL order. This catalog answers what exists and is available; it is not member-earned history.

11.4 Outstanding Checks — account_objects

Use validated Check ledger objects to determine whether a specific Check remains open. Historical CheckCreate, CheckCash, and CheckCancel transactions provide the durable transaction history.

11.5 Authority and allocation history

Resolve the current Owner Wallet from the latest valid OWNER-WALLET authority-state statement. Resolve the current Community Operating Wallet from the latest valid OPERATING-WALLET authority-state statement and resolve historical authority at the ledger position being evaluated. Reconstruct community allocations from valid LEAP Distributor allocation Checks; community ownership comes from the canonical allocation memo namespace.

12. Transaction Validity Rules

Before software turns an XRPL transaction into an official LEAP fact, it must validate every condition required by that protocol act.

  • Data comes from validated ledger history and the transaction succeeded.
  • The XRPL transaction type is permitted for the intended LEAP protocol act.
  • The account that initiated the transaction was authorized for that act at that ledger position.
  • LEAP-moving acts use the canonical LEAP issuer and canonical LEAP currency value.
  • Member-facing recognition identifies the intended member destination and exactly one canonical Badge, Event, or Challenge memo.
  • A new recognition award references either a protocol-defined recognition available under the Protocol Core or a community-defined recognition that already exists and is available at the award's ledger position.
  • A Check-based recognition is pending at CheckCreate and becomes earned only after the matching Check is successfully cashed.
  • A Payment-based recognition becomes earned only when the LEAP Payment successfully validates and delivers LEAP.
  • A community-defined lifecycle record is a no-op AccountSet from the authorized Community Operating Wallet, contains exactly one canonical lifecycle memo, and changes no AccountSet-specific setting. Protocol-defined recognition does not use community lifecycle records.
  • A lifecycle CREATE does not reuse an already-reserved recognition ID.
  • An allocation Check is created by the LEAP Distributor and contains exactly one canonical allocation memo whose amount matches the offered whole-number LEAP amount.
  • Allocation ownership comes from the community namespace in the memo, not from the delivery address.
  • An authority-state record is a no-op AccountSet with exactly one canonical authority-state memo and valid authority for that key.
  • The initial OWNER-WALLET statement is published by the Owner Wallet designated in the Protocol Authority Registry and names that same account; later OWNER-WALLET replacements are published by the Owner Wallet resolved immediately before the transaction.
  • For a previously unestablished Community ID, the initial OPERATING-WALLET statement is published by the current Owner Wallet and names the community's first Operating Wallet.
  • For later OPERATING-WALLET replacements, the sender equals the Operating Wallet resolved immediately before the transaction.
Fail Closed
If required provenance or protocol meaning cannot be established, software may display the transaction as raw/audit history, but it must not convert it into official recognition, Earned LEAP, rank, allocation, lifecycle state, or authority state.

14. Legacy / Pre-Protocol Transactions

Reader software may preserve compatibility with genuine earlier LEAP history so that protocol hardening does not erase the past. New protocol writes use only the current grammar and transaction rules.

Legacy pattern or stateInterpretation rule
Earlier structured or split memo representationsRead-only compatibility after complete authority, asset, destination, result, and semantic validation. Never emit new records in the old form.
Free-form historical memoDo not automatically grant recognition. Map only when provenance and intended meaning can be established under an explicit legacy rule.
Recognition ID established before lifecycle activationMay be treated as a legacy-established definition when supported by valid authorized historical recognition. The ID remains reserved and may later receive END or IGNORE without retroactive CREATE.
Legacy Check with XRPL ExpirationInterpret according to its actual ledger fields. New standard recognition Checks omit expiration.
Pre-authority-state communityUse the documented existing-community migration rule to establish the first canonical OPERATING-WALLET value.
Compatibility Rule
Backward-compatible reading must not make an old draft form current again. Writers follow one current protocol; readers may understand older approved history where necessary.
GREAT-CHAT is not a legacy exception. It is protocol-defined and therefore requires no retroactive or future community lifecycle CREATE. Genuine legacy compatibility remains a separate evidence-based concern.

15. Versioning & Change Control

VersionUse
0.xWorking protocol drafts before the first approved production standard
1.0First hardened production protocol
1.1, 1.2…Additive / backward-compatible protocol changes
2.0Breaking interpretation change

Change rules

  • Protocol changes must be deliberate and documented. Application implementation must not silently redefine protocol meaning.
  • Sections 1–6 define the core model; later sections must conform to that model.
  • Never silently redefine, rename, reassign, or recycle a canonical Community, Badge, Event, or Challenge ID already used on-ledger.
  • Do not add a member-recognition category outside BADGE, EVENT, and CHALLENGE without an explicit protocol revision.
  • Keep older protocol versions readable so historical transactions remain interpretable under the rules that applied to them.
  • Prefer additive changes over breaking changes.
  • The LEAP Distributor is singular. If the Distributor changes, the protocol revision must identify the successor and an unambiguous XRPL activation point so historical Distributor authority remains reconstructable.
  • A change to the LEAP Issuer changes the asset identity and requires an explicit breaking protocol decision; it must never be treated as ordinary wallet rotation.
  • Community Operating Wallet changes use the on-ledger authority-state mechanism in Section 7, not protocol-document edits.
  • UI, signer, navigation, celebration, reminder, and other presentation/operating changes do not require protocol revisions unless they change ledger meaning.

16. Open Decisions Before Protocol 1.0

Only genuine protocol questions belong here. Implementation chores, wallet-specific work, and UI polish do not.

  • Verify the configured LEAP 160-bit currency value against live XRPL state and then remove the verification qualifier from Section 4.
  • Define an emergency recovery rule for a lost, inaccessible, or compromised current Community Operating Wallet.
  • Define the Earned LEAP / rank treatment of any prior awards if a recognition definition is later marked IGNORE. The underlying XRPL token transfers cannot be reversed by the lifecycle marker, but Protocol 1.0 must state whether those amounts remain official Earned LEAP.
