Access Architecture

Who gets into which workspace?

This working document defines the application-access shape Wild Ledger is building toward. It intentionally separates login and workspace access from XRP Ledger authority.

Working architecture · Owner reference · Not LEAP Protocol law
Core rule: Application access chooses the workspace. XRPL authority controls canonical actions.
1 · Product Contract

Three ways into one backend

The finished product should feel different depending on who signs in, while converging on the same community-management pages once a community workspace has been selected.

Owner

Wild Ledger Owner

Signs into the Wild Ledger workspace and lands on the Owner Console. The Owner can see ecosystem-wide metrics, the community directory, provisioning, the full Owner Library, and can drill into a community when needed.

Operator

Community Operator

Signs in as one provisioned community and lands directly inside that community's working view. The Operator should not need to pass through the Owner's community directory.

Demo

Demo Operator

Signs into one designated demonstration community and sees an Operator-style backend for sales and evaluation. Demo access may be intentionally limited even when the screens resemble a real Operator workspace.

2 · Routing Contract

Login selects context; downstream pages converge

The authentication system may change later. The route contract should survive that change.

Owner authentication
↓
owner.html
↓ when drilling into a community
viewCommunity.html?community=<ID>&role=owner
Community Operator authentication
↓
viewCommunity.html?community=<ASSIGNED-ID>&role=operator
Demo Operator authentication
↓
viewCommunity.html?community=<DEMO-ID>&role=operator

Convergence rule

From viewCommunity.html forward, Owner and Operator should use the same community pages wherever practical. Role and authenticated workspace context determine what is shown or allowed; separate duplicate page families should be avoided unless security or a real technical constraint requires them.

3 · Authority Boundary

Login is never XRPL authority

This is the most important boundary in the access design.

Application

Authentication/session may establish

  • Who may enter Wild Ledger.
  • Which workspace they may see.
  • Owner, Operator, or demo application role.
  • Which Community ID is assigned to an Operator session.
  • Server-side permissions for non-canonical application features.
XRPL

Validated ledger history establishes

  • Current Wild Ledger Owner Wallet.
  • Current and historical Community Operating Wallet authority.
  • Canonical LEAP recognition, allocation, lifecycle, and provenance.
  • Whether the wallet signing a protocol action is actually authorized.
A correct password can open a workspace. It can never make an unauthorized XRPL wallet authoritative.
4 · Community Binding

Operators are bound to one provisioned community

Production authentication should supply the community assignment; URL parameters and browser storage may carry that context through the UI but must not be trusted as the source of authorization.

Real Operator session

The authenticated server-side session should say, in effect, “this Operator may enter Community ABCD.” The application can then route directly to ABCD's community view.

Owner session

The Owner may browse the community directory and deliberately enter ABCD as Owner. That is a different application role, but the community's canonical XRPL actions still require the appropriate ledger-authorized wallet.

5 · Library Visibility

Operator handbook versus Owner design room

The Library is intentionally different by role.

Operator Library

Operations Manual

The Operator-facing Library should present the Operations Manual: the handbook needed to operate a Wild Ledger community.

Owner Library

Full working shelf

The Owner sees the Operations Manual, LEAP Protocol material, architecture documents, working papers, experiments, and other Wild Ledger reference material.

Security note

Visibility is not yet access control

Today these are static HTML pages. Hiding a link from an Operator view does not make the underlying file private. Production privacy requires authenticated server-side authorization or another genuine access-control boundary.

6 · Demo Workspace

A sales demo should feel real without granting real authority

One designated demo community can let a prospective Operator explore the backend without turning a demonstration credential into control of canonical XRPL actions.

What a prospect should be able to understand

Community dashboard, Recognition, Tokenomics, Checkbook, Setup, and the Operations Manual should communicate what day-to-day community operation feels like.

What the demo credential must not imply

Possession of a demo username or password must not grant an XRPL signing key, change canonical Operating Wallet authority, or authorize live protocol transactions.

7 · Current Scaffold

What exists today

This section is descriptive, so a future developer or AI can distinguish the present test harness from the intended contract.

Implemented test routing

getWild.html

The current sign-in page is explicitly a temporary test harness. The Access key is ignored. A case-insensitive prefix of owner routes to owner.html. A case-insensitive prefix of operator currently routes to community ZHR in Operator mode.

Current context carrier

Query string + sessionStorage

Role and community values currently travel through URL parameters and browser session storage. They are useful UI context only and must not be mistaken for authenticated authority.

Community convergence

viewCommunity.html

Owner and Operator already converge on the same community working page. The page changes navigation according to role and carries the same role/community context into Tokenomics, Recognition, Checkbook, Library, and Setup.

Ledger authority

communityAuthority.js and XRPL

Protocol-critical community authority is reconstructed from validated XRP Ledger history. This is already the correct authority model and should remain independent of whichever authentication provider is eventually selected.

8 · Production Security Seam

What future authentication must provide

The provider is intentionally undecided. The contract is more important than the vendor.

  • Authenticate the user on the server side. Do not infer authorization from a URL or editable browser value.
  • Issue a session containing the allowed application role and, for Operators, the assigned Community ID.
  • Protect Owner-only pages and data at a real authorization boundary. UI hiding alone is presentation.
  • Provide clean logout and session expiry.
  • Support a designated demo Operator session with intentionally limited permissions.
  • Preserve the XRPL boundary. Canonical actions must still resolve current ledger authority and require the authorized wallet's signature.
