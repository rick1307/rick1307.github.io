Choose the authority path that matches the community. Wild Ledger keeps the paths separate because the wallet allowed to establish authority is different in each case.

Normal path

Create a New Community

Use this when the community has never existed in Wild Ledger. Wild Ledger generates a new 3-character Community ID and the current Wild Ledger Owner Wallet establishes its first Community Operating Wallet on XRPL.

Who signs? The current canonical Wild Ledger Owner Wallet.
What becomes canonical? The new Community ID and its first Operating Wallet become canonical together when the XRPL transaction validates.

Legacy path

Establish an Existing Community

Use this only for a community that existed before Wild Ledger's current on-ledger authority system and therefore needs its one-time authority establishment.

Who signs? The community's existing Operating Wallet establishes itself. The Wild Ledger Owner does not create this legacy authority statement.
Why isn't this wired yet? The older helper in the current code is an Owner-signed new-community tool, so it is not the correct implementation for this legacy case.

Operating Wallet changes are handled somewhere else. Once a community has canonical authority, a later Operating Wallet change belongs inside that community. The currently authorized Community Operating Wallet names its successor.
Application access chooses the workflow. XRPL authority determines who may perform the canonical act.
