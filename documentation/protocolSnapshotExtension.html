Protocol Snapshot Extension

A teaching sketch for one narrow extension to the existing LEAP protocol: how a dedicated snapshot transaction could preserve small, periodic observations about the community and later turn those observations into historical charts.

Ledger History Protocol Extensibility
Status: notional. Nothing on this page is adopted protocol. It documents the current working idea so it can be tested, challenged, simplified, or discarded before any namespace or grammar is made authoritative.

1. Start with the question, not the encoding

Ledger History now shows two live facts: how many organized crew members exist and how many wallets currently possess LEAP.

Live metricTotal Crew Members

A measure of the organized community that has formally come aboard.

Live metricTotal LEAP Holders

A measure of how far LEAP has escaped beyond the organized community and into the wild.

Those numbers answer what is true now. The next question is historical: how did those numbers change over time?

A chart needs historical observations. A snapshot is simply one durable observation of the system at one moment.

2. A snapshot is its own kind of record

The extension keeps one existing LEAP habit: do not combine unrelated record types.

Badge

A badge transaction is about a badge.

Challenge

A challenge transaction is about a challenge.

Snapshot

A snapshot transaction is about system measurements.

This means a snapshot would not be tucked inside a badge, event, challenge, or other transaction merely to save a fee. It would stand on its own, be signed on its own, and have one job.

One record class per transaction. Do not mix meanings just because they happen on the same day.

3. One snapshot can contain many related measurements

“One record class per transaction” does not mean “one number per transaction.” A snapshot is naturally a bundle of measurements taken at the same moment.

The boundary is semantic: measurements that describe the same system snapshot may travel together. Unrelated record types do not.

4. The current notional one-line record

The working idea is to place the entire snapshot language in a single memo-data value:

SFL-LEAP/SNAPSHOT=C/27|H/43

That one line contains both identity and payload. No second memo subfield is required by this design.

Record identitySFL-LEAP/SNAPSHOT

Tells the LEAP decoder what kind of record this is.

=
Snapshot payloadC/27|H/43

Carries the measurements observed at that moment.

In this notional form, the extension would leave other memo subfields unused rather than assigning them jobs merely because they exist.

5. Read the grammar from left to right

The line is deliberately simple enough to decode by eye.

SFL-LEAP
The LEAP namespace.
/SNAPSHOT
The record class. This transaction records a system snapshot.
=
Everything after this point is snapshot data.
C/27
C means Crew. The observed crew count is 27.
|
Delimiter: another snapshot observation follows.
H/43
H means Holders. The observed holder count is 43.
The protocol does not need to store a sentence. It only needs enough structure for the decoder to reconstruct the meaning.

6. Store observations. Derive relationships.

The two charts need only two stored measurements because the ledger transaction itself supplies the observation time.

If a value can always be recreated from facts already stored, the extension should prefer calculation over permanent duplication.

7. One snapshot can feed several views

The same breadcrumb can support multiple outputs without writing multiple records.

ChartCrew History

Read C from each snapshot and plot it against transaction time.

DerivedLEAP Reach

For each snapshot, calculate H ÷ C. No extra ledger field required.

ChartHolder History

Read H from each snapshot and plot it against transaction time.

8. The snapshot grammar can grow without changing shape

The current notional keys are intentionally minimal:

C = Crew count
H = Holder count

If a future metric earns its place, the same grammar can append another observation:

SFL-LEAP/SNAPSHOT=C/27|H/43|X/12

The important point is that X would not be assigned merely because there is room. It would receive meaning only when a real historical question justifies storing that observation permanently.

The number of delimiters is not the design limit. Meaning is the design limit. Add a key only when the observation is worth remembering.

9. A decoder should be tolerant of future keys

A simple reader can split the payload into key/value pairs:

record = "SFL-LEAP/SNAPSHOT=C/27|H/43|X/12"

1. confirm prefix: SFL-LEAP/SNAPSHOT=
2. take everything after =
3. split observations at |
4. split each observation at /
5. recognize keys we understand
6. ignore unknown keys until the protocol defines them

This gives the snapshot format a useful form of forward compatibility: older software could continue reading C and H even if a later extension introduces another recognized snapshot key.

10. The proposed daily workflow

The extension becomes useful only when the site can reliably decide whether a new observation should be recorded.

01

Ledger History loads and calculates the current live metrics.

02

The page checks whether the reporting period already has a snapshot record.

03

If a snapshot already exists, the page reads it and does nothing else.

04

If one is missing, the page can offer the manager a prompt to record the current snapshot.

05

The manager approves and signs one dedicated snapshot transaction.

06

Once validated, that transaction becomes another historical observation available to future charts.

The exact cadence — daily, weekly, or something else — remains a design choice. The extension defines how a snapshot could be represented, not how often it must be written.

11. What this extension deliberately does not do

  • It does not replace the existing badge, event, challenge, or other LEAP record classes.
  • It does not combine unrelated record types into one transaction.
  • It does not permanently assign meanings to future snapshot keys before they are needed.
  • It does not store values such as Reach when they can be derived from stored observations.
  • It does not commit the current delimiters or key names as final protocol.
  • It does not require a second protocol generation. It is an extension concept that can be evaluated alongside the existing protocol.

12. The extension in one sentence

A snapshot is a dedicated LEAP transaction that records several related measurements from one moment in one compact, self-contained memo-data line, so the website can later reconstruct historical charts without mixing snapshots with other LEAP record types.

The current teaching example is:

SFL-LEAP/SNAPSHOT=C/27|H/43

Crew and Holders are observations. Reach is a relationship. The observations are remembered; the relationship is calculated.

This page is a design note, not an adopted specification. It intentionally preserves open questions about cadence, signing workflow, final delimiters, key registry, and whether additional snapshot measurements are valuable enough to record permanently.
