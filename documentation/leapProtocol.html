LEAP Protocol

A working standard for how LEAP is identified, distributed, named, queried, interpreted, and used to establish membership, rank, events, challenges, badges, and permanent recognition on the XRP Ledger.

1. Purpose

The LEAP Protocol exists so that every future page, script, distribution, badge rule, and XRPL query interprets LEAP in the same way.

LEAP Standard
This document is the operating source of truth for how LEAP canonical ledger facts are interpreted. Public-facing pages may simplify these rules, but they should not silently invent different ones.

This protocol deliberately separates current state from historical fact. Current state answers questions such as “How much LEAP does this wallet hold now?” Historical fact answers questions such as “Was this wallet officially awarded Panama Crew?”

2. Core Principles

Current State Membership, balance, current rank, outstanding objects.
Historical State Awards, recognition lifecycle markers, events, distributions, provenance, dates, transaction hashes.
Authority Only the approved XRPL authority for a transaction type can create official LEAP protocol facts.
Canonical State Principle
Canonical state exists only on XRPL. Wild Ledger is an interpreter of canonical state, never its keeper. Any fact required to reconstruct authoritative Wild Ledger state MUST be recoverable from validated XRPL ledger history. Off-ledger storage, browser storage, configuration files, caches, or presentation logic MUST NOT constitute authoritative protocol state.

Operating rules

  • Use validated XRPL data for every canonical fact and for decisions that affect membership, rank, recognition, or protocol state.
  • Never treat a memo by itself as proof of official LEAP recognition.
  • Always verify LEAP currency identity and issuer identity together.
  • Never use a display label as the canonical machine identifier.
  • Once a canonical identifier has been used on-ledger, do not rename or reuse it.
  • Rank is dynamic. Historical recognition is permanent unless an explicit future revocation rule is created.
  • Each website page may query XRPL independently unless a future architecture change explicitly replaces that rule.
Design Principle — Automatic Stabilizers
LEAP should prefer rules that are enforced or naturally reinforced by the ledger itself rather than by a growing pile of manual administration. Canonical identifiers reduce ambiguity; Check state prevents ordinary duplicate issuance; the seven-day Manager cleanup policy limits how long an unattended Check normally remains open; validated history preserves the record; and owner reserve makes large numbers of open Checks consume real working capital. The reserve is not a fee or burn. It is temporary capital tied up while the ledger object remains open, which provides a useful anti-spam and discipline mechanism.

3.1 Community Operating Account succession

A community is not its wallet. The community namespace and identity remain continuous while the XRPL account authorized to operate that community may change over time. Wild Ledger starts from the community's immutable authority root account and reconstructs every later handoff from validated XRPL history.

LEAP Standard
The authority root is a fixed protocol trust anchor, not mutable application state. The current Community Operating Account is never established by a browser setting, local storage value, or editable configuration field. It is derived by applying completed on-ledger authority transitions in sequence.

A routine authority handoff uses the next sequential identifier AUTH-NNN and requires two validated no-op AccountSet records:

<COMMUNITY>-LEAP/COMMUNITY/AUTHORITY/AUTH-NNN/SUCCESSOR=<NEW-ACCOUNT>
<COMMUNITY>-LEAP/COMMUNITY/AUTHORITY/AUTH-NNN/PREDECESSOR=<OLD-ACCOUNT>
  • The SUCCESSOR record must be signed by the Community Operating Account that is current at that ledger position.
  • The matching PREDECESSOR record must be signed by the proposed successor account.
  • The transition becomes effective only after both records are validated. Until then, the predecessor remains the current authority.
  • The transition's effective ledger is the later of the two validating ledger indexes. Protocol actions from the predecessor after that point are not authoritative.
  • Authority transition IDs begin at AUTH-001, advance sequentially, and are interpreted within one community namespace.
  • A successor may not create a cycle by returning authority to an account already used earlier in the same authority chain.
  • If more than one uncanceled successor is proposed for the same transition ID, readers fail closed rather than guessing which account is authoritative.

A pending proposal may be canceled by the still-current predecessor before successor acceptance:

<COMMUNITY>-LEAP/COMMUNITY/AUTHORITY/AUTH-NNN/CANCEL-SUCCESSOR=<NEW-ACCOUNT>
Signer Independence
The XRPL account is the authority; the wallet application is only a signer. An operator may move between Bifrost, Xaman, Tangem, hardware devices, or another compatible signer without changing the Community Operating Account. A protocol authority change is needed only when the XRPL account itself changes.
Recovery is separate from routine rotation. If the predecessor account is lost and cannot sign, an owner/recovery authority path must be defined by a later explicit protocol revision. Routine two-party rotation must not be weakened to solve that exceptional case.

6. Namespace & Memo Standard

LEAP uses public memo strings across permitted XRPL transaction types. The memo namespace identifies the protocol meaning, while the XRPL TransactionType is also part of the interpretation. The root namespace is SFL-LEAP.

LEAP Standard
A member recognition award uses <COMMUNITY>-LEAP/<CATEGORY>=<VALUE> on the canonical recognition transaction. A recognition lifecycle marker uses <COMMUNITY>-LEAP/RECOGNITION/<CATEGORY>/<CANONICAL-ID>/LIFECYCLE-TAG=<ACTION> on a canonical no-op AccountSet. The current lifecycle actions are CREATE, END, and IGNORE.

Memo location, token scope, and community namespaces

XRPL Fact
Memos is a common XRPL transaction field, so different transaction types can carry LEAP protocol data. A member recognition memo belongs to the CheckCreate transaction that creates the Check. A recognition lifecycle memo belongs to the no-op AccountSet transaction that publishes the lifecycle statement. Neither memo belongs to an individual LEAP token or to a Check ledger object. Cashing uses a separate CheckCash transaction, and canceling uses a separate CheckCancel transaction.
LEAP is fungible. A memo does not travel with one specific LEAP coin or unit. The memo is part of the transaction record, not an individually serialized LEAP unit.
Community Namespace Rule
A community namespace lets Wild Ledger software separate that community's LEAP records from unrelated wallet activity and organize them into the community's badges, events, challenges, member history, and administrative history. Each participating community can use its own namespace and conventions within the LEAP protocol.

Community naming convention

Participating communities use a common naming pattern so Wild Ledger software can recognize and organize community records consistently while keeping each community distinct.

RuleStandard
Community memo formatEach community uses its own namespace followed by a category and value: <COMMUNITY>-LEAP/<CATEGORY>=<VALUE>.
Recognition categoriesThe standard categories are BADGE, EVENT, and CHALLENGE. Examples include <COMMUNITY>-LEAP/BADGE=LEAP-OG, <COMMUNITY>-LEAP/EVENT=COMMUNITY-MEETUP, and <COMMUNITY>-LEAP/CHALLENGE=LEAP-001.

Current Production Convention
One Check. One recognition. One reason. One line in the logbook. A Check may carry one or more whole LEAP, but it records exactly one Badge, Event, or Challenge recognition. Do not bundle multiple recognitions into one Check. If a member earns two separate recognitions, create two separate Checks.

Canonical grammar rules

  • The prefix is exactly SFL-LEAP/.
  • The category is one of BADGE, EVENT, or CHALLENGE. No fourth recognition category is implied by onboarding, rank, origin, or protocol metadata.
  • NEW-MEMBER is a Badge: SFL-LEAP/BADGE=NEW-MEMBER.
  • Use one equals sign between category and value: =.
  • The value uses uppercase ASCII letters, numbers, and hyphens only.
  • Challenge values use the form LEAP-NNN, beginning with LEAP-001.
  • Do not add spaces around separators.
  • Do not append a date merely to duplicate the ledger timestamp. Add time or other qualifiers when they are needed to make a recurring recognition canonically distinct.
  • The vertical bar character (|) is not part of the current recognition memo grammar and must not be used to bundle multiple recognitions into one Check.
  • A lifecycle marker uses the self-identifying path RECOGNITION/<CATEGORY>/<CANONICAL-ID>/LIFECYCLE-TAG, where <CATEGORY> is exactly BADGE, EVENT, or CHALLENGE.
  • The lifecycle action value is exactly CREATE, END, or IGNORE.
  • The canonical recognition ID in the lifecycle path follows the same canonical ID rules used by member recognition memos for that category.
  • A canonical lifecycle AccountSet carries exactly one decoded public LEAP lifecycle memo. The lifecycle memo is self-identifying; a second recognition-identity memo is not required.
  • Once a canonical recognition ID has been established, it is permanently reserved. IDs are never recycled after END or IGNORE.

Ledger-discovered recognition vocabulary

The XRPL is the working registry of canonical recognition IDs and their lifecycle. The normal recognition interface keeps the categories fixed at BADGE, EVENT, and CHALLENGE, then reconstructs recognition state from validated protocol history rather than from a separate database.

Implementation Rule
Under the lifecycle model, a brand-new Badge, Event, or Challenge is born when the authorized Community Operating Wallet publishes a valid self-identifying CREATE lifecycle AccountSet. An END lifecycle marker ends its normal active/available life without erasing the identifier, prior awards, or ledger history. An IGNORE lifecycle marker permanently suppresses an erroneous or invalid recognition from normal recognition views while preserving it in administrative ledger history. Failed transactions, malformed memos, matching text from unauthorized accounts, and mutating AccountSet transactions do not establish lifecycle state.
Recognition IDs established before lifecycle markers are activated remain readable from valid authorized historical CheckCreate records. Before software requires CREATE as the mandatory birth record for all newly created IDs, the lifecycle activation point must be recorded so legacy history remains deterministic.
XRPL Fact
XRPL transactions can contain a Memos array. A memo can use the protocol fields MemoType, MemoFormat, and MemoData, which are represented as hexadecimal in transaction JSON. Wallet software may expose these fields through a simpler user interface.
Implementation Rule
The LEAP protocol standardizes the decoded public text, not a particular wallet's field layout. In Xaman's Check workflow, enter the complete canonical string into the single public memo box. Reader software should decode the transaction memo fields, normalize the wallet representation, and accept only a string that matches the LEAP grammar above.
Earlier draft structures may still be read for backward compatibility, but they are not used for new issuance. ORIGIN and PROTOCOL are not current member-recognition categories. Protocol versions belong to this operating document and its change log.

7.2 Minimum checks for a canonical recognition CheckCreate

  • TransactionType = CheckCreate
  • Account is an authorized LEAP distributor
  • Destination is the intended member wallet
  • SendMax.currency is the canonical LEAP currency value
  • SendMax.issuer is the LEAP issuer
  • SendMax.value is a positive whole-number LEAP amount; fractional LEAP is not used by protocol policy
  • The normal LEAP recognition Check omits the XRPL Expiration field
  • Transaction is successful
  • Transaction is in validated ledger history
  • Exactly one canonical SFL-LEAP/<CATEGORY>=<VALUE> public memo records the recognition reason

7.3 Issuance controls: amount, visibility, and cleanup

The recognition identity comes from the canonical memo. Delivery timing is handled operationally rather than by putting an expiration on the normal Check.

ControlProtocol / interface rule
LEAP amountPositive whole numbers only. The normal form starts blank so the issuer must enter the amount deliberately. Zero is never submitted.
XRPL ExpirationThe normal LEAP recognition Check sets no on-ledger expiration. The Check remains cashable until it is cashed or canceled.
Member Record noticeA pending no-expiration Check is shown to the member for 7 days from the validated CheckCreate ledger timestamp, then the notice is hidden on day 8. Hiding the notice does not cancel or expire the Check.
Manager cleanup flagThe Manager Checkbook marks an open no-expiration Check Cleanup Due after 7 days. This is a Manager-side operating rule only; it does not change the ledger object.
Cleanup actionRick decides when to cancel an unwanted or stale Check. A validated CheckCancel removes the Check object and releases its owner reserve.
Legacy expirationsReaders remain compatible with older Checks that contain an XRPL Expiration. Those legacy Checks are interpreted according to their actual ledger expiration.
If the validated creation timestamp cannot be established, software must not invent a seven-day age. Member Record may keep the notice visible and the Checkbook may report that cleanup age is unavailable until authoritative timing can be determined.

7.4 Recognition uniqueness and duplicate suppression

Normal LEAP issuance treats the recipient address plus the exact canonical recognition as the duplicate key. Amount, age, and cleanup status do not create a different recognition.

LEAP Standard
Same destination address + same exact canonical recognition = duplicate. The normal Create Check interface should not offer a recognition while an open Check for that exact recognition still exists for the recipient, even after the seven-day cleanup flag appears, or after the recipient has already redeemed it. A canceled unredeemed Check reopens the recognition. A legacy Check that truly expired on-ledger may also reopen it.
Earlier state for same recipient + recognitionNormal Create Check behavior
Open Check, including 7+ days oldSuppress the recognition choice; do not create a second pending Check while the original Check still exists.
Successfully redeemed / cashedSuppress the recognition choice; the exact recognition is already part of that recipient's history.
Canceled and unredeemedRecognition may be offered again.
Legacy expired and unredeemedRecognition may be offered again. If the expired Check object still exists, clean it up separately.
Deliberate duplicate or “plus-up” issuance is an exceptional manual action, not a normal software path. If ever needed, it should be performed judgmentally outside the standard Create Check interface, for example manually in Xaman. The standard interface is intentionally designed to make ordinary duplicates impossible rather than merely warn about them.

7.5 Trust lines are not part of the issuer workflow

A recipient does not need to establish a LEAP trust line before the distributor creates a Check. The Create Check interface therefore does not require, warn about, or preflight a destination trust line as a condition of issuance. When an issued-token Check is cashed, XRPL can automatically create the trust line needed to hold the token with a zero limit. After cashing, that trust line remains as needed to hold the recipient's LEAP balance.

Why LEAP Uses Checks
Checks separate recognition issuance from recipient token setup. The distributor can record and deliver the recognition first; the recipient establishes the holding relationship by cashing the Check. This lowers onboarding friction while preserving an authoritative CheckCreate history for the LEAP logbook.

7.6 Check linkage

Store or derive the Check ledger object's ID from the successful CheckCreate metadata. A later CheckCash.CheckID can be matched back to that exact Check.

7.7 Direct Payment fallback

Direct LEAP Payments may be valid when deliberately used. When determining the amount actually delivered by a Payment, use transaction metadata rather than assuming the requested amount equals the delivered amount. The Check workflow remains the current onboarding and recognition standard.

7.8 Xaman Check cleanup procedure

Xaman separates the historical transaction from the live Check ledger object. The All tab in Events shows the historical CheckCreate transaction. The actionable open Check is found under Planned.

LEAP Operating Procedure
When the manager Checkbook identifies a Cleanup Due, legacy-expired, or otherwise unwanted outstanding Check, open the LEAP Distributor wallet in Xaman and use Events → Planned → Check → Cancel Check. After the CheckCancel transaction validates, the Check ledger object is removed and the XRP owner reserve associated with that Check is released.
Current XRPL State
At this revision, each open Check created by the distributor increases its owner reserve by 0.2 XRP. The manager Checkbook should read the network's current reserve value rather than assume that 0.2 XRP will remain permanent. The owner reserve is temporary working capital, not a transaction fee; it becomes available again when the Check object is removed.
The seven-day cleanup rule is not expiration. A normal LEAP Check that is 7+ days old remains cashable because no XRPL expiration was set. The Manager Checkbook merely marks it for cleanup so Rick can decide whether to cancel it. For older legacy Checks that do contain an expiration, expiration and cancellation are still different: expiration stops cashing, but only a valid CheckCancel removes the ledger object and releases owner reserve.

7.9 Recognition lifecycle markers — no-op AccountSet

Recognition lifecycle is recorded separately from member recognition awards. A lifecycle record moves no LEAP and names no member. It is a signed protocol statement made by the Community Operating Wallet about one recognition object.

XRPL Fact
AccountSet is a different XRPL transaction type from CheckCreate. It supports the common Memos field. If none of the AccountSet-specific setting fields are supplied, the transaction has no account-setting effect beyond consuming the normal transaction cost.
Canonical Lifecycle Transaction
A canonical recognition lifecycle record must be a successful, validated no-op AccountSet sent by the Community Operating Wallet currently authorized for that community namespace. It must contain exactly one decoded public LEAP lifecycle memo in the self-identifying form <COMMUNITY>-LEAP/RECOGNITION/<CATEGORY>/<CANONICAL-ID>/LIFECYCLE-TAG=<ACTION>. It must not contain AccountSet-specific fields that change account state.
Lifecycle actionProtocol meaning
CREATEBirth of the identified recognition. A Badge becomes Available; a Challenge becomes Active; an Event becomes Active.
ENDNormal terminal lifecycle marker. Its user-facing meaning depends on recognition type: Badge = Retired and no longer selectable for new awards; Challenge = Closed and no longer active/completable; Event = Completed and no longer active. Prior valid awards remain valid and visible.
IGNOREExceptional terminal marker for an erroneous, invalid, test, or otherwise non-operational recognition object. The record remains part of XRPL history, but compliant Wild Ledger clients exclude it from normal Available, Active, and History recognition lists and clearly annotate it as Ignored in owner/operator ledger or audit views.

  • The lifecycle action is exactly CREATE, END, or IGNORE
Cradle-to-Grave Rule
CREATE begins the recognition's protocol lifecycle. END is the normal terminal state, interpreted according to recognition type. IGNORE is an exceptional terminal state. Neither END nor IGNORE erases XRPL history. Under the current protocol there is no reopen, unend, or unignore action; any future reversal rule requires an explicit protocol revision.
Permanent ID Reservation
A canonical recognition ID is never recycled. Before creating a new Badge, Challenge, or Event, Wild Ledger must validate the proposed ID against the complete XRPL-derived recognition history for that community and category. Any ID that has already been established — whether currently Available/Active, later ended, or later marked IGNORE — is unavailable for reuse. Ignored IDs remain permanently reserved and must be visibly annotated as Ignored in owner/operator ledger views.
Recognition IDs established before explicit lifecycle markers are activated remain readable from valid authorized historical CheckCreate records and are treated as legacy-established IDs for namespace-reservation purposes. They may later receive a valid END or IGNORE lifecycle marker without first requiring a retroactive CREATE. The lifecycle activation point must remain documented so legacy history is deterministic.

9. Badge & Historical Recognition Rules

A badge represents something the wallet owner actually did, attended, contributed to, or was officially recognized for. NEW-MEMBER is a Badge; onboarding does not create a separate recognition category.

Badge Lifecycle
A valid CREATE marker makes a Badge Available. A later valid END marker makes it Retired and places it in recognition History. Retirement ends future normal issuance; it does not erase earlier awards.

Badge validity test

VALIDATED

10. Event & Challenge Rules

Event

Event Lifecycle
A valid CREATE marker makes an Event Active. A later valid END marker makes it Completed and places it in recognition History.

A specific real-world or community occasion connected to a LEAP distribution or recognition. Example: LA-CRUZ-BEACH-BONFIRE-2026.

LEAP Standard
The XRPL validated timestamp records when the recognition transaction was actually issued. The canonical EVENT identifier describes which event the recognition means. If the same or similar event occurs again, make the new identifier more specific using the broad-to-narrow convention from Section 5 rather than relying on timestamp alone to distinguish two recognitions. Date components are acceptable when they identify the occurrence itself.

Challenge

Challenge Lifecycle
A valid CREATE marker makes a Challenge Active. A later valid END marker makes it Closed and places it in recognition History.

A defined participation opportunity. Challenges receive unique sequential IDs and are never recycled. Example: LEAP-001. The next challenge receives the next unused number.

LEAP Standard
Event, challenge, badge, and rank are separate concepts. Do not overload one identifier to mean another. For a given recipient, the exact same canonical Event, Challenge, or Badge is normally recognized only once through the standard issuance interface.

12. Transaction Validity Rules

Before website code treats an XRPL transaction as an official LEAP fact, validate all applicable conditions.

  • Data is from validated ledger history
  • Transaction result indicates success
  • Transaction type is allowed for the intended interpretation
  • For LEAP-moving recognition transactions, issuer matches the canonical LEAP issuer
  • For LEAP-moving recognition transactions, currency matches the canonical LEAP currency value
  • Authority account is authorized for the specific transaction type and protocol action
  • Destination or affected wallet matches the member being evaluated when the protocol action concerns a member
  • Memo fields decode successfully when memo-based protocol data is required
  • A recognition CheckCreate normalizes to exactly one canonical <COMMUNITY>-LEAP/<CATEGORY>=<VALUE> record
  • A lifecycle AccountSet normalizes to exactly one lifecycle tag plus exactly one canonical recognition identity, with matching community namespaces
  • The category is recognized and the value is a valid canonical identifier

14. Legacy / Pre-Protocol Transactions

Reader software may preserve compatibility with earlier LEAP memo experiments and pre-lifecycle recognition history so genuine historical records remain readable. New member-recognition issuance and new lifecycle statements must use the current transaction-specific grammars from Sections 6 and 7.

Legacy patternInterpretationRule
MemoType=SFL-LEAP + MemoData=BADGE=...Earlier structured LEAP formRead-only compatibility after full authority, asset, destination, and validation checks
MemoType=SFL-LEAP/BADGE + MemoData=...Earlier split-memo proposalRead-only compatibility; do not create new records this way
Raw LEAP-OG or another free-form memoPotential pre-protocol markerDo not automatically grant recognition; map it manually only after provenance is verified
No LEAP recognition memoOrdinary earlier LEAP transfer/checkDo not infer badge, event, or challenge meaning without another authoritative rule
Canonical Badge/Event/Challenge first seen in authorized CheckCreate history before lifecycle activationPre-lifecycle canonical recognition IDKeep readable as valid historical vocabulary; do not require a retroactive CREATE marker
Backward-compatible readers are intentionally more tolerant than the production writer. The writer follows one current grammar; readers may understand older approved forms without making those forms current again.

15. Versioning & Change Control

VersionUse
0.xWorking drafts before the first production standard
1.0First approved production protocol
1.1, 1.2…Additive / backward-compatible rules
2.0Breaking interpretation change

Change rules

  • Never silently redefine an identifier already used on-ledger.
  • Never reuse a retired badge, event, or challenge ID for a different meaning.
  • Do not add a recognition category outside BADGE, EVENT, and CHALLENGE without an explicit protocol revision.
  • When a recurring recognition needs distinction, extend the canonical ID from broad to narrow rather than redefining an existing ID.
  • Record newly authorized protocol authorities here before treating their transaction-type-specific actions as official.
  • Keep old protocol versions readable so historical transactions remain interpretable.
  • Prefer additive changes over breaking changes.

16. Open Decisions / Next Work

These are intentionally unresolved or implementation work still required before declaring Protocol 1.0.

  • Verify and record LEAP's exact 160-bit currency value from the live ledger.
  • Record the LEAP genesis / first relevant ledger index for efficient historical queries.
  • Inventory existing pre-protocol LEAP transactions and complete any legacy mapping rules that are actually needed.
  • Complete live verification of the Create Check / Review Check writer against Sections 5–7, including whole-number amount, no on-ledger expiration, canonical memo preview, duplicate suppression, and Xaman signing.
  • Verify the ledger-discovered Badge/Event/Challenge vocabulary, lifecycle reconstruction, and duplicate-state logic against live XRPL history.
  • Record the lifecycle activation ledger index before making CREATE mandatory for all newly created recognition IDs, so pre-lifecycle Check-discovered IDs remain deterministically readable.
  • Complete the first live SFL AUTH-001 operating-account handoff and verify that Wild Ledger reconstructs the new current authority from XRPL without a mutable off-ledger current-wallet setting.
  • Maintain the challenge sequence so each new challenge receives the next unused LEAP-NNN identifier, derived from canonical ledger history rather than a separate database counter.
