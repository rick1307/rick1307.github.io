LEAP Protocol

A working standard for how LEAP is identified, distributed, named, queried, interpreted, and used to establish membership, rank, events, challenges, badges, and permanent recognition on the XRP Ledger.

1. Purpose

The LEAP Protocol exists so that every future page, script, distribution, badge rule, and XRPL query interprets LEAP in the same way.

LEAP Standard
This document is the operating source of truth for LEAP. Public-facing pages may simplify these rules, but they should not silently invent different ones.

This protocol deliberately separates current state from historical fact. Current state answers questions such as “How much LEAP does this wallet hold now?” Historical fact answers questions such as “Was this wallet officially awarded Panama Crew?”

2. Core Principles

Current State Membership, balance, current rank, outstanding objects.
Historical State Awards, events, distributions, provenance, dates, transaction hashes.
Authority Only approved issuer/distributor activity can create official LEAP recognition.

Operating rules

  • Use validated XRPL data for decisions that affect membership, rank, or recognition.
  • Never treat a memo by itself as proof of official LEAP recognition.
  • Always verify LEAP currency identity and issuer identity together.
  • Never use a display label as the canonical machine identifier.
  • Once a canonical identifier has been used on-ledger, do not rename or reuse it.
  • Rank is dynamic. Historical recognition is permanent unless an explicit future revocation rule is created.
  • Each website page may query XRPL independently unless a future architecture change explicitly replaces that rule.
Design Principle — Automatic Stabilizers
LEAP should prefer rules that are enforced or naturally reinforced by the ledger itself rather than by a growing pile of manual administration. Canonical identifiers reduce ambiguity; Check state prevents ordinary duplicate issuance; the seven-day Manager cleanup policy limits how long an unattended Check normally remains open; validated history preserves the record; and owner reserve makes large numbers of open Checks consume real working capital. The reserve is not a fee or burn. It is temporary capital tied up while the ledger object remains open, which provides a useful anti-spam and discipline mechanism.

XRPL Fact
Standard XRPL currency codes are three characters. Nonstandard currency codes use a 160-bit hexadecimal value. Because LEAP is four letters, code must compare against the actual on-ledger currency value rather than assuming every API will return the literal text LEAP.

Human-facing names may be friendly and change over time. Canonical IDs are for machines and must remain stable.

LEAP Standard
Canonical IDs use uppercase ASCII letters, numbers, and hyphens only. Avoid spaces, underscores, punctuation, apostrophes, emojis, and decorative capitalization. Once used on-ledger, an ID is permanent.

Broad-to-narrow specificity

When a recurring or similar real-world recognition needs to be distinguished from an earlier one, extend the identifier from the broadest concept toward progressively narrower qualifiers. Add only as much specificity as is needed to make the intended recognition unambiguous.

6. Namespace & Memo Standard

LEAP uses one short public memo string to identify the project, the recognition category, and the canonical value. The root namespace is SFL-LEAP.

LEAP Standard
The canonical public memo grammar is SFL-LEAP/<CATEGORY>=<VALUE>. One Check records one recognition reason, so one canonical recognition Check carries one public LEAP memo.

Current recognition categories

CategoryWhat it recordsCanonical example
BADGEPermanent recognition for something the member did, contributed to, attended, or was recognized forSFL-LEAP/BADGE=NEW-MEMBER
EVENTA specific real-world or community occasion connected to the awardSFL-LEAP/EVENT=LA-CRUZ-BEACH-BONFIRE-2026
CHALLENGEA numbered LEAP participation challengeSFL-LEAP/CHALLENGE=LEAP-001
Current Production Convention
One Check. One recognition. One reason. One line in the logbook. A Check may carry one or more whole LEAP, but it records exactly one Badge, Event, or Challenge recognition. Do not bundle multiple recognitions into one Check. If a member earns two separate recognitions, create two separate Checks.

Canonical grammar rules

  • The prefix is exactly SFL-LEAP/.
  • The category is one of BADGE, EVENT, or CHALLENGE. No fourth recognition category is implied by onboarding, rank, origin, or protocol metadata.
  • NEW-MEMBER is a Badge: SFL-LEAP/BADGE=NEW-MEMBER.
  • Use one equals sign between category and value: =.
  • The value uses uppercase ASCII letters, numbers, and hyphens only.
  • Challenge values use the form LEAP-NNN, beginning with LEAP-001.
  • Do not add spaces around separators.
  • Do not append a date merely to duplicate the ledger timestamp. Add time or other qualifiers when they are needed to make a recurring recognition canonically distinct.
  • The vertical bar character (|) is not part of the current recognition memo grammar and must not be used to bundle multiple recognitions into one Check.

Production examples

SFL-LEAP/BADGE=NEW-MEMBER
SFL-LEAP/BADGE=FIRST-MEMBER
SFL-LEAP/BADGE=PANAMA-CREW-2026
SFL-LEAP/EVENT=LA-CRUZ-BEACH-BONFIRE-2026
SFL-LEAP/CHALLENGE=LEAP-001

Ledger-discovered recognition vocabulary

The XRPL is the working registry of canonical recognition IDs. The normal Create Check interface keeps the Reason choices fixed at BADGE, EVENT, and CHALLENGE, then discovers the existing values for the selected category from validated, protocol-compliant CheckCreate history produced by an authorized LEAP distributor.

Implementation Rule
The first canonical use of a brand-new Badge, Event, or Challenge value may be created manually in Xaman or through another authorized protocol-compliant writer. Once that successful CheckCreate appears in validated distributor history, the value becomes discoverable by the website and may be offered as a future choice. Failed transactions, malformed memos, and matching text from unauthorized accounts do not populate the recognition vocabulary.
Once a canonical ID has appeared in valid authorized history, the ID remains part of the protocol vocabulary even if the individual Check later expires or is canceled. Check state affects whether that recognition may be issued again to a particular recipient; it does not erase the identifier itself.
XRPL Fact
XRPL transactions can contain a Memos array. A memo can use the protocol fields MemoType, MemoFormat, and MemoData, which are represented as hexadecimal in transaction JSON. Wallet software may expose these fields through a simpler user interface.
Implementation Rule
The LEAP protocol standardizes the decoded public text, not a particular wallet's field layout. In Xaman's Check workflow, enter the complete canonical string into the single public memo box. Reader software should decode the transaction memo fields, normalize the wallet representation, and accept only a string that matches the LEAP grammar above.
Earlier draft structures may still be read for backward compatibility, but they are not used for new issuance. ORIGIN and PROTOCOL are not current member-recognition categories. Protocol versions belong to this operating document and its change log.

LEAP Standard
When a Check is used to deliver official recognition, the recognition memo belongs on the CheckCreate transaction because that transaction is created by the authorized LEAP distributor. The later CheckCash claims the Check; it does not replace the original recognition record. The CheckCreate remains in validated transaction history even after the temporary Check ledger object is removed.

7.2 Minimum checks for a canonical recognition CheckCreate

  • TransactionType = CheckCreate
  • Account is an authorized LEAP distributor
  • Destination is the intended member wallet
  • SendMax.currency is the canonical LEAP currency value
  • SendMax.issuer is the LEAP issuer
  • SendMax.value is a positive whole-number LEAP amount; fractional LEAP is not used by protocol policy
  • The normal LEAP recognition Check omits the XRPL Expiration field
  • Transaction is successful
  • Transaction is in validated ledger history
  • Exactly one canonical SFL-LEAP/<CATEGORY>=<VALUE> public memo records the recognition reason

7.3 Issuance controls: amount, visibility, and cleanup

The recognition identity comes from the canonical memo. Delivery timing is handled operationally rather than by putting an expiration on the normal Check.

ControlProtocol / interface rule
LEAP amountPositive whole numbers only. The normal form starts blank so the issuer must enter the amount deliberately. Zero is never submitted.
XRPL ExpirationThe normal LEAP recognition Check sets no on-ledger expiration. The Check remains cashable until it is cashed or canceled.
Crew Record noticeA pending no-expiration Check is shown to the member for 7 days from the validated CheckCreate ledger timestamp, then the notice is hidden on day 8. Hiding the notice does not cancel or expire the Check.
Manager cleanup flagThe Manager Checkbook marks an open no-expiration Check Cleanup Due after 7 days. This is a Manager-side operating rule only; it does not change the ledger object.
Cleanup actionRick decides when to cancel an unwanted or stale Check. A validated CheckCancel removes the Check object and releases its owner reserve.
Legacy expirationsReaders remain compatible with older Checks that contain an XRPL Expiration. Those legacy Checks are interpreted according to their actual ledger expiration.
If the validated creation timestamp cannot be established, software must not invent a seven-day age. Crew Record may keep the notice visible and the Checkbook may report that cleanup age is unavailable until authoritative timing can be determined.

7.4 Recognition uniqueness and duplicate suppression

Normal LEAP issuance treats the recipient address plus the exact canonical recognition as the duplicate key. Amount, age, and cleanup status do not create a different recognition.

LEAP Standard
Same destination address + same exact canonical recognition = duplicate. The normal Create Check interface should not offer a recognition while an open Check for that exact recognition still exists for the recipient, even after the seven-day cleanup flag appears, or after the recipient has already redeemed it. A canceled unredeemed Check reopens the recognition. A legacy Check that truly expired on-ledger may also reopen it.
Earlier state for same recipient + recognitionNormal Create Check behavior
Open Check, including 7+ days oldSuppress the recognition choice; do not create a second pending Check while the original Check still exists.
Successfully redeemed / cashedSuppress the recognition choice; the exact recognition is already part of that recipient's history.
Canceled and unredeemedRecognition may be offered again.
Legacy expired and unredeemedRecognition may be offered again. If the expired Check object still exists, clean it up separately.
Deliberate duplicate or “plus-up” issuance is an exceptional manual action, not a normal software path. If ever needed, it should be performed judgmentally outside the standard Create Check interface, for example manually in Xaman. The standard interface is intentionally designed to make ordinary duplicates impossible rather than merely warn about them.

7.5 Trust lines are not part of the issuer workflow

A recipient does not need to establish a LEAP trust line before the distributor creates a Check. The Create Check interface therefore does not require, warn about, or preflight a destination trust line as a condition of issuance. When an issued-token Check is cashed, XRPL can automatically create the trust line needed to hold the token with a zero limit. After cashing, that trust line remains as needed to hold the recipient's LEAP balance.

Why LEAP Uses Checks
Checks separate recognition issuance from recipient token setup. The distributor can record and deliver the recognition first; the recipient establishes the holding relationship by cashing the Check. This lowers onboarding friction while preserving an authoritative CheckCreate history for the LEAP logbook.

7.6 Check linkage

Store or derive the Check ledger object's ID from the successful CheckCreate metadata. A later CheckCash.CheckID can be matched back to that exact Check.

7.7 Direct Payment fallback

Direct LEAP Payments may be valid when deliberately used. When determining the amount actually delivered by a Payment, use transaction metadata rather than assuming the requested amount equals the delivered amount. The Check workflow remains the current onboarding and recognition standard.

7.8 Xaman Check cleanup procedure

Xaman separates the historical transaction from the live Check ledger object. The All tab in Events shows the historical CheckCreate transaction. The actionable open Check is found under Planned.

LEAP Distributor wallet
↓
Xaman → Events
↓
Planned
↓
Open the Check object
↓
Cancel Check
LEAP Operating Procedure
When the manager Checkbook identifies a Cleanup Due, legacy-expired, or otherwise unwanted outstanding Check, open the LEAP Distributor wallet in Xaman and use Events → Planned → Check → Cancel Check. After the CheckCancel transaction validates, the Check ledger object is removed and the XRP owner reserve associated with that Check is released.
Current XRPL State
At this revision, each open Check created by the distributor increases its owner reserve by 0.2 XRP. The manager Checkbook should read the network's current reserve value rather than assume that 0.2 XRP will remain permanent. The owner reserve is temporary working capital, not a transaction fee; it becomes available again when the Check object is removed.
The seven-day cleanup rule is not expiration. A normal LEAP Check that is 7+ days old remains cashable because no XRPL expiration was set. The Manager Checkbook merely marks it for cleanup so Rick can decide whether to cancel it. For older legacy Checks that do contain an expiration, expiration and cancellation are still different: expiration stops cashing, but only a valid CheckCancel removes the ledger object and releases owner reserve.

9. Badge & Historical Recognition Rules

A badge represents something the wallet owner actually did, attended, contributed to, or was officially recognized for. NEW-MEMBER is a Badge; onboarding does not create a separate recognition category.

Badge validity test

VALIDATED
AND transaction result = success
AND originating account = authorized distributor
AND destination = member wallet
AND currency = canonical LEAP currency
AND issuer = canonical LEAP issuer
AND decoded public memo matches SFL-LEAP/BADGE=<CANONICAL-ID>
LEAP Standard
A matching memo created by an unauthorized wallet does not establish a badge. Provenance and content must both validate. The authoritative badge vocabulary is discovered from valid authorized on-ledger history, not from a separately maintained website-only list.

10. Event & Challenge Rules

Event

A specific real-world or community occasion connected to a LEAP distribution or recognition. Example: LA-CRUZ-BEACH-BONFIRE-2026.

LEAP Standard
The XRPL validated timestamp records when the recognition transaction was actually issued. The canonical EVENT identifier describes which event the recognition means. If the same or similar event occurs again, make the new identifier more specific using the broad-to-narrow convention from Section 5 rather than relying on timestamp alone to distinguish two recognitions. Date components are acceptable when they identify the occurrence itself.

Challenge

A defined participation opportunity. Challenges receive unique sequential IDs and are never recycled. Example: LEAP-001. The next challenge receives the next unused number.

LEAP Standard
Event, challenge, badge, and rank are separate concepts. Do not overload one identifier to mean another. For a given recipient, the exact same canonical Event, Challenge, or Badge is normally recognized only once through the standard issuance interface.

12. Transaction Validity Rules

Before website code treats an XRPL transaction as an official LEAP fact, validate all applicable conditions.

  • Data is from validated ledger history
  • Transaction result indicates success
  • Transaction type is allowed for the intended interpretation
  • Issuer matches the canonical LEAP issuer
  • Currency matches the canonical LEAP currency value
  • Authority account is authorized for the action
  • Destination or affected wallet matches the member being evaluated
  • Memo fields decode successfully when memo-based recognition is required
  • The decoded public memo normalizes to exactly one canonical SFL-LEAP/<CATEGORY>=<VALUE> record
  • The category is recognized and the value is a valid canonical identifier
LEAP Standard
Fail closed. If required provenance cannot be established, the website may display the transaction as history, but it must not convert it into official LEAP recognition.

14. Legacy / Pre-Protocol Transactions

Reader software may preserve compatibility with earlier LEAP memo experiments so genuine historical records remain readable. New issuance must use the canonical single-string format from Section 6.

Legacy patternInterpretationRule
MemoType=SFL-LEAP + MemoData=BADGE=...Earlier structured LEAP formRead-only compatibility after full authority, asset, destination, and validation checks
MemoType=SFL-LEAP/BADGE + MemoData=...Earlier split-memo proposalRead-only compatibility; do not create new records this way
Raw LEAP-OG or another free-form memoPotential pre-protocol markerDo not automatically grant recognition; map it manually only after provenance is verified
No LEAP recognition memoOrdinary earlier LEAP transfer/checkDo not infer badge, event, or challenge meaning without another authoritative rule
Backward-compatible readers are intentionally more tolerant than the production writer. The writer follows one current grammar; readers may understand older approved forms without making those forms current again.

15. Versioning & Change Control

VersionUse
0.xWorking drafts before the first production standard
1.0First approved production protocol
1.1, 1.2…Additive / backward-compatible rules
2.0Breaking interpretation change

Change rules

  • Never silently redefine an identifier already used on-ledger.
  • Never reuse a retired badge, event, or challenge ID for a different meaning.
  • Do not add a recognition category outside BADGE, EVENT, and CHALLENGE without an explicit protocol revision.
  • When a recurring recognition needs distinction, extend the canonical ID from broad to narrow rather than redefining an existing ID.
  • Record newly authorized distributors here before treating their transactions as official.
  • Keep old protocol versions readable so historical transactions remain interpretable.
  • Prefer additive changes over breaking changes.

16. Open Decisions / Next Work

  • Verify and record LEAP's exact 160-bit currency value from the live ledger.
