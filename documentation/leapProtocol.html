LEAP Protocol

A working standard for how LEAP is identified, distributed, named, queried, interpreted, and used to establish membership, rank, events, challenges, badges, owner-to-community operations, and permanent records on the XRP Ledger.

1. Purpose

The LEAP Protocol exists so that every future page, script, distribution, badge rule, and XRPL query interprets LEAP in the same way.

LEAP Standard
This document is the operating source of truth for LEAP. Public-facing pages may simplify these rules, but they should not silently invent different ones.

This protocol deliberately separates current state from historical fact. Current state answers questions such as “How much LEAP does this wallet hold now?” Historical fact answers questions such as “Was this wallet officially awarded Panama Crew?”

2. Core Principles

Current State Membership, balance, current rank, outstanding objects.
Historical State Awards, events, distributions, provenance, dates, transaction hashes.
Authority Each protocol action must originate from the wallet role authorized for that action.

Operating rules

  • Use validated XRPL data for decisions that affect membership, rank, or recognition.
  • Never treat a memo by itself as proof of official LEAP recognition.
  • Always verify LEAP currency identity and issuer identity together.
  • Never use a display label as the canonical machine identifier.
  • Once a canonical identifier has been used on-ledger, do not rename or reuse it.
  • Rank is dynamic. Historical recognition is permanent unless an explicit future revocation rule is created.
  • Each website page may query XRPL independently unless a future architecture change explicitly replaces that rule.
Design Principle — Automatic Stabilizers
LEAP should prefer rules that are enforced or naturally reinforced by the ledger itself rather than by a growing pile of manual administration. Canonical identifiers reduce ambiguity; Check state prevents ordinary duplicate issuance; the seven-day Manager cleanup policy limits how long an unattended Check normally remains open; validated history preserves the record; and owner reserve makes large numbers of open Checks consume real working capital. The reserve is not a fee or burn. It is temporary capital tied up while the ledger object remains open, which provides a useful anti-spam and discipline mechanism.

3. Authority Registry

LEAP uses distinct wallet roles. The Global Issuing Wallet controls the asset, the Global Distribution Wallet provisions communities, and each community operates through its own registered Community Operating Wallet. These roles must not be collapsed merely because one person may currently control more than one of them.

6. Namespace & Memo Standard

LEAP uses one short public memo string as a compact protocol record. The same one-field grammar can describe different relationships while the originating and destination wallet roles determine what the record means.

LEAP Standard
The canonical public memo grammar is <COMMUNITY>-LEAP/<TYPE>=<VALUE>. For Sailing Frog's Leap, the root namespace is SFL-LEAP. New protocol writing uses one complete canonical string in the single public memo field.

6.1 Memo location, token scope, and community namespaces

XRPL Fact
The public LEAP memo belongs to the CheckCreate transaction that creates the Check. It does not belong to an individual LEAP token or to the Check ledger object itself. Cashing uses a separate CheckCash transaction, and canceling uses a separate CheckCancel transaction. The original CheckCreate and its memo remain in validated public ledger history either way.
LEAP is fungible. A memo does not travel with one specific LEAP coin or unit. The memo is part of the transaction record, not an individually serialized LEAP unit.
Community Namespace Rule
A community namespace lets Wild Ledger software separate that community's records from unrelated wallet activity. The namespace can be used for member recognition and for owner-to-community administrative history without exposing that administrative layer in the ordinary member experience.

6.2 Protocol families: who is acting for whom

Protocol records are interpreted in the context of the relationship between the actors. The same grammar is reused, but the allowed record types and required wallet roles are different.

RelationshipType / StateMeaningCanonical example

Protocol Boundary
BADGE, EVENT, and CHALLENGE are the current member-recognition categories. ALLOCATION is not a fourth recognition category. It is the first Owner → Community operational record type. Rank is also separate: it is calculated state rather than a memo record.

6.4 One field, one purpose

Current Production Convention
One Check. One purpose. One canonical memo. One line in the appropriate logbook. A Community → Member recognition Check records exactly one Badge, Event, or Challenge reason. An Owner → Community allocation Check records exactly one Allocation. Do not bundle multiple protocol purposes into one Check.

6.5 Canonical grammar rules

  • The general prefix is <COMMUNITY>-LEAP/. For Sailing Frog's Leap it is exactly SFL-LEAP/.
  • The current recognition types are BADGE, EVENT, and CHALLENGE.
  • The current Owner → Community operational type is ALLOCATION.
  • NEW-MEMBER is a Badge: SFL-LEAP/BADGE=NEW-MEMBER.
  • Use one equals sign between type and value: =.
  • Canonical text uses uppercase ASCII letters, numbers, and hyphens where an identifier is required.
  • Challenge values use the form LEAP-NNN, beginning with LEAP-001.
  • Allocation values are positive whole-number LEAP amounts and must equal the Check's LEAP amount.
  • Do not add spaces around separators.
  • Do not append a date merely to duplicate the ledger timestamp. Add time or another qualifier only when it is needed to distinguish the meaning of a recognition.
  • The vertical bar character (|) is not part of the current protocol memo grammar and must not be used to bundle multiple protocol purposes into one Check.

6.6 Ledger-discovered recognition vocabulary

The XRPL is the working registry of canonical recognition IDs. The normal Create Check interface keeps the Recognition choices fixed at BADGE, EVENT, and CHALLENGE, then discovers the existing values for the selected category from validated, protocol-compliant CheckCreate history produced by that community's registered Community Operating Wallet.

Implementation Rule
The first canonical use of a brand-new Badge, Event, or Challenge value may be created manually in Xaman or through another authorized protocol-compliant writer using the community's registered Community Operating Wallet. Once that successful CheckCreate appears in validated history, the value becomes discoverable by the website and may be offered as a future choice. Failed transactions, malformed memos, and matching text from unauthorized accounts do not populate the recognition vocabulary.

Once a canonical recognition ID has appeared in valid authorized history, the ID remains part of the protocol vocabulary even if the individual Check later expires or is canceled. Check state affects whether that recognition may be issued again to a particular recipient; it does not erase the identifier itself.

XRPL Fact
XRPL transactions can contain a Memos array. A memo can use the protocol fields MemoType, MemoFormat, and MemoData, which are represented as hexadecimal in transaction JSON. Wallet software may expose these fields through a simpler user interface.
Implementation Rule
The LEAP protocol standardizes the decoded public text, not a particular wallet's field layout. In Xaman's Check workflow, enter the complete canonical string into the single public memo box. Reader software should decode the transaction memo fields, normalize the wallet representation, and accept only a string that matches the LEAP grammar above. Earlier draft structures may still be read for backward compatibility, but they are not used for new issuance. ORIGIN and PROTOCOL are not current protocol record types. Protocol versions belong to this operating document and its change log.

Business Meaning
The Global Distribution Wallet is used to provision communities in deliberate operating chunks, including recurring subscription allocations when applicable. The Community Operating Wallet then handles that community's member-level activity. This separation keeps global provisioning history distinct from day-to-day community recognition.
A pending Allocation Check is a commitment offered to the community, not LEAP already received by the community. A canceled or otherwise unredeemed Allocation Check is not included in completed Community Allocation. If allocation-specific expiration or cleanup rules are adopted later, they must be added explicitly rather than inferred from the member-recognition seven-day display policy.

7.5 Recognition issuance controls: amount, visibility, and cleanup

Recognition identity comes from the canonical recognition memo. Delivery timing is handled operationally rather than by putting an expiration on the normal member recognition Check.

ControlProtocol / interface rule
LEAP amountPositive whole numbers only. The normal form starts blank so the manager must enter the amount deliberately. Zero is never submitted.
XRPL ExpirationThe normal member recognition Check sets no on-ledger expiration. The Check remains cashable until it is cashed or canceled.
Member Record noticeA pending no-expiration recognition Check is shown to the member for 7 days from the validated CheckCreate ledger timestamp, then the notice is hidden on day 8. Hiding the notice does not cancel or expire the Check.
Manager cleanup flagThe Manager Checkbook marks an open no-expiration recognition Check Cleanup Due after 7 days. This is a Manager-side operating rule only; it does not change the ledger object.
Cleanup actionThe Community Manager decides when to cancel an unwanted or stale recognition Check. A validated CheckCancel removes the Check object and releases its owner reserve.
Legacy expirationsReaders remain compatible with older Checks that contain an XRPL Expiration. Those legacy Checks are interpreted according to their actual ledger expiration.
If the validated creation timestamp cannot be established, software must not invent a seven-day age. Member Record may keep the notice visible and the Checkbook may report that cleanup age is unavailable until authoritative timing can be determined.

7.6 Recognition uniqueness and duplicate suppression

Normal LEAP recognition issuance treats the recipient address plus the exact canonical recognition as the duplicate key. Amount, age, and cleanup status do not create a different recognition.

LEAP Standard
Same destination address + same exact canonical recognition = duplicate. The normal Create Check interface should not offer a recognition while an open Check for that exact recognition still exists for the recipient, even after the seven-day cleanup flag appears, or after the recipient has already redeemed it. A canceled unredeemed Check reopens the recognition. A legacy Check that truly expired on-ledger may also reopen it.
Earlier state for same recipient + recognitionNormal Create Check behavior
Open Check, including 7+ days oldSuppress the recognition choice; do not create a second pending Check while the original Check still exists.
Successfully redeemed / cashedSuppress the recognition choice; the exact recognition is already part of that recipient's history.
Canceled and unredeemedRecognition may be offered again.
Legacy expired and unredeemedRecognition may be offered again. If the expired Check object still exists, clean it up separately.
Deliberate duplicate or “plus-up” recognition issuance is an exceptional manual action, not a normal software path. If ever needed, it should be performed judgmentally outside the standard Create Check interface, for example manually in Xaman. The standard interface is intentionally designed to make ordinary duplicates impossible rather than merely warn about them.

7.7 Trust lines are not part of the recognition writer workflow

A member does not need to establish a LEAP trust line before the Community Operating Wallet creates a recognition Check. The Create Check interface therefore does not require, warn about, or preflight a destination trust line as a condition of issuance. When an issued-token Check is cashed, XRPL can automatically create the trust line needed to hold the token with a zero limit. After cashing, that trust line remains as needed to hold the recipient's LEAP balance.

Why LEAP Uses Checks
Checks separate record creation and delivery from recipient setup and acceptance. For member recognition, the Community Operating Wallet can create the recognition first and the member claims it by cashing the Check. For allocations, the Global Distribution Wallet can create a traceable provisioning record and the Community Operating Wallet completes it by cashing the Check. In both cases the validated CheckCreate remains useful for the appropriate LEAP logbook.

7.8 Check linkage

Store or derive the Check ledger object's ID from the successful CheckCreate metadata. A later CheckCash.CheckID can be matched back to that exact Check. The same linkage is used to determine whether a recognition or Allocation is pending, completed, or canceled.

7.9 Direct Payment fallback

Direct LEAP Payments may be valid when deliberately used. When determining the amount actually delivered by a Payment, use transaction metadata rather than assuming the requested amount equals the delivered amount. The Check workflow remains the current member-recognition standard and the current Owner → Community Allocation standard. A direct Payment must not be silently reclassified as an ALLOCATION unless a future protocol revision explicitly defines that behavior.

7.10 Xaman Check cleanup procedure

Xaman separates the historical transaction from the live Check ledger object. The All tab in Events shows the historical CheckCreate transaction. The actionable open Check is found under Planned.

Wallet that created the Check
↓
Xaman → Events
↓
Planned
↓
Open the Check object
↓
Cancel Check
LEAP Operating Procedure
When a stale or unwanted outstanding Check should be canceled, open the wallet that created that Check in Xaman and use Events → Planned → Check → Cancel Check. For member recognition this is normally the relevant Community Operating Wallet. For an Allocation it is the Global Distribution Wallet. After the CheckCancel transaction validates, the Check ledger object is removed and the XRP owner reserve associated with that Check is released.
Current XRPL State
At this revision, each open Check increases its creating account's owner reserve by 0.2 XRP. Software should read the network's current reserve value rather than assume that 0.2 XRP will remain permanent. The owner reserve is temporary working capital, not a transaction fee; it becomes available again when the Check object is removed.
The seven-day cleanup rule applies to the current member-recognition workflow; it is not an Allocation rule. A normal member recognition Check that is 7+ days old remains cashable because no XRPL expiration was set. For older legacy Checks that do contain an expiration, expiration and cancellation are still different: expiration stops cashing, but only a valid CheckCancel removes the ledger object and releases owner reserve.

10. Event & Challenge Rules

Event

A specific real-world or community occasion connected to a LEAP distribution or recognition. Example: LA-CRUZ-BEACH-BONFIRE-2026.

LEAP Standard
The XRPL validated timestamp records when the recognition transaction was actually issued. The canonical EVENT identifier describes which event the recognition means. If the same or similar event occurs again, make the new identifier more specific using the broad-to-narrow convention from Section 5 rather than relying on timestamp alone to distinguish two recognitions. Date components are acceptable when they identify the occurrence itself.

Challenge

A defined participation opportunity. Challenges receive unique sequential IDs and are never recycled. Example: LEAP-001. The next challenge receives the next unused number.

LEAP Standard
Event, challenge, badge, and rank are separate concepts. Do not overload one identifier to mean another. For a given recipient, the exact same canonical Event, Challenge, or Badge is normally recognized only once through the standard issuance interface.

12. Transaction Validity Rules

Before website code treats an XRPL transaction as an official LEAP fact, validate all conditions applicable to the intended interpretation.

  • Data is from validated ledger history
  • Transaction result indicates success
  • Transaction type is allowed for the intended interpretation
  • Issuer matches the Global Issuing Wallet
  • Currency matches the canonical LEAP currency value
  • Originating wallet is authorized for the protocol record type
  • Destination matches the actor required by that protocol relationship
  • Memo fields decode successfully when a memo-based protocol record is required
  • The decoded public memo normalizes to exactly one canonical <COMMUNITY>-LEAP/<TYPE>=<VALUE> record
  • The type is recognized and the value satisfies that type's rules
  • For BADGE, EVENT, and CHALLENGE, the origin is the registered Community Operating Wallet for the namespace and the destination is the intended member
  • For ALLOCATION, the origin is the Global Distribution Wallet, the destination is the registered Community Operating Wallet for the namespace, and the memo amount equals the Check amount
LEAP Standard
Fail closed. If required provenance cannot be established, the website may display the transaction as ledger history, but it must not convert it into official LEAP recognition or a completed Wild Ledger Allocation.

15. Versioning & Change Control

VersionUse
0.xWorking drafts before the first production standard
1.0First approved production protocol

Change rules

  • Never silently redefine an identifier already used on-ledger.
  • Never reuse a retired badge, event, or challenge ID for a different meaning.
  • Do not add a member-recognition category outside BADGE, EVENT, and CHALLENGE without an explicit protocol revision.
  • Do not add an Owner → Community operational type beyond ALLOCATION without an explicit protocol revision.
  • When a recurring recognition needs distinction, extend the canonical ID from broad to narrow rather than redefining an existing ID.
  • Register each Community Operating Wallet before treating its community-originated recognition as official.
  • Record any change to the Global Issuing Wallet or Global Distribution Wallet here before treating the new authority as official.
  • Keep old protocol versions readable so historical transactions remain interpretable.
  • Prefer additive changes over breaking changes.
