Wild Ledger · Architecture & Development Plan

Multi-Community Initiative

The game plan for evolving Sailing Frog's Leap from a single-community application into one Wild Ledger platform capable of serving many independently branded LEAP communities.

Working plan

Purpose of this document

This document is the durable reference for the Wild Ledger multi-community transition. It should contain enough context to restart development after a break without reconstructing the strategy from old conversations.

Do not sell the multi-community system until it works smoothly for both Sailing Frog's Leap and Zach's Hot Rods.

Zach's Hot Rods is the fictional proving community. Sailing Frog's Leap remains the real production community.

The core architecture

One LEAP

Wild Ledger communities use the same LEAP asset. Communities do not issue separate versions of LEAP.

One application

There should be one shared application codebase rather than a separate copy of the site for every community.

Many communities

Each community gets its own configuration, identity, namespace, distributor, imagery, copy and appearance.

Configuration controls identity. Code controls behavior.

Community model

The same application should be able to become a different community by loading a different community configuration.

Wild Ledger application
│
├── Sailing Frog's Leap
│   ├── community ID: sfl
│   ├── namespace: SFL-LEAP
│   ├── distributor
│   ├── branding / images
│   └── community copy
│
└── Zach's Hot Rods
    ├── community ID: zachs-hot-rods
    ├── namespace: ZACH-LEAP
    ├── test distributor
    ├── hot-rod branding / images
    └── fictional community copy

Future communities such as Warriors XRP or Sailing Doodles would follow the same pattern without duplicating the application.

The proving test

The question the architecture must answer

Can the exact same application operate Sailing Frog's Leap and Zach's Hot Rods simply by changing community configuration?

If the answer is yes across the complete user and manager workflow, the Wild Ledger architecture has been proven at the two-community level. If Zach requires duplicate versions of core application pages or special one-off logic, the architecture needs more work.

What belongs in configuration

The initial configuration model should remain deliberately small. Add configuration fields because the communities genuinely need to differ, not merely because something could theoretically be configurable.

Identity

Community name, community ID, LEAP namespace and community-specific labels.

XRPL

Community distributor address and other community-specific public XRPL settings required by the application.

Appearance

Logo, a small number of standard image slots, accent choices and other controlled branding.

Copy

Welcome text and limited community-specific language where the shared application needs it.

Community operators may create their own images using AI, photography, artwork or existing branding. Wild Ledger should define the image slots and dimensions; it does not need to create their artwork. Sensible defaults should exist when optional images are not supplied.

What must stay shared

Core behavior must not fork by community. The objective is to preserve one maintainable application.

  • One crewRecord.html, not a separate Crew Record for every community.
  • One manager.html, not community-specific Manager pages.
  • One ranks / achievement system implementation.
  • One XRPL interaction layer.
  • One implementation of Checks, ledger history, state handling and future shared features.
  • Bug fixes and improvements should become available to every community from the shared codebase.

Zach's Hot Rods

Zach's Hot Rods is intentionally fictional. It provides a safe second community with branding radically different from Sailing Frog's Leap.

Community: Zach's Hot Rods
Community ID: zachs-hot-rods
Namespace: ZACH-LEAP
LEAP asset: Same LEAP used by Sailing Frog's Leap
Distributor: Test wallet during development
Achievements: Fictional hot-rod Badges, Events and Challenges
Appearance: Intentionally different from Sailing Frog's Leap

Zach exists to expose hidden Sailing Frog assumptions. Anything that unexpectedly changes Zach when SFL changes—or requires Zach-specific application code—should be examined as a possible architecture problem.

Transition plan

1

Freeze the baseline

Begin from a fresh, complete source-of-truth snapshot of the working Sailing Frog's Leap site. Do not reconstruct the transition from remembered or accumulated edits.

2

Create the community configuration layer

Introduce a shared configuration mechanism, initially containing SFL and Zach. Do not change working behavior simply for the sake of refactoring.

3

Move branding out first

Move community name, visual identity, selected images and community-specific copy from hard-coded pages into configuration. Confirm SFL still looks and behaves correctly.

4

Move protocol identity

Move namespace and distributor-specific settings into configuration. This is where SFL and Zach must begin operating independently while using the same shared application logic.

5

Exercise the complete Zach workflow

Run Zach through the same lifecycle expected of a real community: entry, join, Crew Record, LEAP recognition, Checks, achievements, ledger/history views, Manager tools and any other live workflow.

6

Build Community Settings

Once the configuration model is proven, create a controlled communitySettings.html experience for the fields that should be manageable without editing application code.

7

Regression test SFL and Zach together

Every important workflow must work for both communities without community-specific copies of core pages. Changes made for one community must not corrupt the other.

8

Only then prepare real onboarding

After the two-community test is stable, convert the proven Zach onboarding process into the repeatable process used for the first real Wild Ledger community.

LEAP economics currently assumed

This initiative is primarily an application-architecture plan, but the current Wild Ledger offer affects what Manager and reporting will eventually need to expose.

  • Community setup: free.
  • Wild Ledger membership: 10 XRP per month.
  • Starting allocation: 1,000 LEAP.
  • Additional LEAP is not sold directly.
  • Replenishment is available on request at 110% of the LEAP distributed since the previous replenishment.
  • Example: distribute 500 LEAP, then request a 550 LEAP replenishment.
  • The mechanism rewards circulation. It does not judge why a community chose to award LEAP.
  • Once LEAP has been distributed to a member, Wild Ledger does not control what that member does with it.

The Manager / ledger tooling should eventually make the relevant distribution total and available replenishment obvious enough that neither the community operator nor Wild Ledger has to calculate it manually.

Definition of success

The initiative is ready to move from prototype to real prospect onboarding only when all of the following are true:

  • Sailing Frog's Leap continues to work normally.
  • Zach's Hot Rods works end-to-end using the same core application.
  • SFL and Zach have visibly different identities without duplicated core pages.
  • Each community uses its own namespace and distributor configuration correctly.
  • Community-specific ledger and Manager information does not bleed between communities.
  • A shared code change can improve both communities without manually patching two sites.
  • The steps required to create a third community are understood and repeatable.
SFL + Zach first. Real customers second.

The fictional second community is not a demo shortcut. It is the proof that Wild Ledger is actually a platform rather than a renamed copy of the Sailing Frog's Leap website.

Development guardrails

  • Protect the working Sailing Frog's Leap experience throughout the transition.
  • Use a fresh source-of-truth snapshot before substantial structural work.
  • Do not create one GitHub repository per community as the intended architecture.
  • Do not duplicate core HTML or JavaScript simply to make Zach work.
  • Do not over-engineer configuration before a real difference between SFL and Zach requires it.
  • Keep private credentials out of community configuration. Configuration should contain only information appropriate to the application's architecture and security model.
  • Test each migration step before moving the next hard-coded assumption into configuration.
